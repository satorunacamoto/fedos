# Nonce Generation Policy (binding, docs only — no code)

**Status: this document adds no code.** It is Stage 134 of the **Nonce /
Random / Secret lifecycle implementation-prep** docs-only batch — the last
safety-design step before the Implementation Phase (per
`docs/implementation_phase_roadmap.md` §1 item 1) begins. It fixes the
POLICY that `docs/public_random_boundary.md` (Stage 103) and
`docs/public_random_design.md` (Stage 104) deliberately deferred: which
nonce scheme this codebase uses, how a nonce is sourced, and how (key,
nonce) reuse is prevented. Nothing under `src/`, `packages/`, `Cargo.toml`,
or `test/` is changed by this document, and no nonce is generated anywhere
in this codebase today.

This is a safety contract, not an implementation spec. It complements —
and does not renegotiate — `docs/fedos_core_rust_safety.md` §7
("Randomness policy... No nonce reuse... forbidden"),
`docs/vault_crypto_identity.md` §3 ("Nonce discipline: never reuse a (key,
nonce) pair"), `docs/crypto_test_vectors.md` §4 and §9 (nonce reuse is a
required negative test case and a forbidden practice), and the two public
boundary design docs named above. Where this document and any of those
disagree, the earlier, binding safety-rule docs win — this document only
fills in the policy gap they left open on purpose.

---

## 1. Purpose

- **Fix the nonce scheme before any byte-producing code exists.** Per
  `docs/implementation_phase_roadmap.md` §2, this precedes the
  `randomBytes` implementation deliberately: `getrandom` is already
  adopted (Stage 104), so implementation is close, and a real AEAD
  implementation (a later, separate stage) must have a written nonce
  contract to build against instead of inventing one under implementation
  pressure.
- **Policy, not implementation.** No nonce byte is generated by this
  document. `FedosNonceBoundary`/`fedos_nonce_boundary_status()` (Stage
  103) remain byte-for-byte unchanged, still permanently `Unavailable`.
- **Binding on any future encrypt/AEAD stage.** Any stage that later
  implements `encrypt`/`decrypt` (`docs/fedos_core_public_api_design.md`
  §12 step 5) must follow this policy for nonce sourcing, or open a new,
  explicitly-reviewed stage to renegotiate it in the open — never diverge
  silently.

## 2. AEAD nonce reuse is forbidden, unconditionally

- **Reusing a (key, nonce) pair is catastrophic and is forbidden**, full
  stop — this restates, and does not weaken,
  `docs/fedos_core_rust_safety.md` §7 and `docs/vault_crypto_identity.md`
  §3. For any AEAD construction this crate might implement
  (ChaCha20-Poly1305, AES-256-GCM — both already vector-verified under
  `cargo test`, Stage 75/81/101), encrypting two distinct plaintexts under
  the same key with the same nonce is a confidentiality break, not a
  degraded-security edge case.
- **This applies per key, not per process/session.** A key that survives
  across multiple operations (e.g. a derived conversation key reused for
  several messages) carries the non-reuse obligation for its entire
  lifetime, not just within a single call.

## 3. ChaCha20-Poly1305 nonce policy

- **96-bit (12-byte) nonce**, per RFC 8439 — the dependency already
  adopted (Stage 74) and vector-verified (Stage 75/81).
- A 96-bit random nonce has a meaningful birthday-bound collision risk
  once a single key is used for a very large number of messages (the
  classic "random nonce exhaustion" concern for 96-bit constructions).
  This policy does not select a per-key message-count ceiling today — that
  is deferred to the future stage that fixes real key-rotation/session
  scoping — but flags it here so it is not forgotten once real encryption
  exists.
- **XChaCha20-Poly1305 (192-bit / 24-byte nonce)** remains a listed
  candidate (`docs/crypto_test_vectors.md` §2, `docs/vault_crypto_identity.md`
  §3) precisely because its much larger nonce space makes pure-random
  nonce generation safe at far higher message volumes without a counter.
  It has **no adopted dependency and no vectors today** — adopting it is
  its own future, separate stage if the 96-bit exhaustion concern above
  is judged to matter for a real usage pattern.

## 4. AES-GCM nonce policy

- **96-bit (12-byte) nonce**, per NIST SP 800-38D — the dependency already
  adopted (Stage 101) and vector-verified against NIST CAVP vectors the
  same stage.
- AES-GCM's 96-bit nonce carries the same random-nonce birthday-bound
  caveat as §3, and additionally: **AES-GCM nonce misuse is generally
  considered less forgiving than ChaCha20-Poly1305's** in the wider
  cryptographic literature (partial-block/forbidden-attack style failure
  modes under nonce reuse are well documented for GCM). This policy does
  not select AES-GCM over ChaCha20-Poly1305 or vice versa for any future
  default — `docs/fedos_core_public_api_design.md` §5 already fixes that
  the caller picks by label — it only records that GCM's nonce discipline
  requirement is at least as strict as ChaCha20-Poly1305's, never looser.

## 5. Random nonce vs. counter nonce

| Property | Random nonce | Counter nonce |
|---|---|---|
| Source | CSPRNG (`getrandom`, once adopted for real use) | Persisted monotonic state |
| Collision risk | Birthday-bound (non-zero, shrinks with larger nonce space) | Zero, IF the counter never repeats, resets, or is reused across a key |
| State to persist | None | A counter value, durably, across every process restart |
| Failure mode if source misbehaves | Weak/predictable bytes (rare, `getrandom` failure) | Counter reset/rollback/duplication (state-management bug, restart, clock/VM snapshot restore) |
| Fits this codebase's current architecture | Yes — no code anywhere persists crypto state across restarts yet | No — would be the FIRST piece of durable crypto state this codebase has ever needed |

- **A random nonce needs a good CSPRNG and accepts a small, well-understood
  collision probability.** A counter nonce needs a good CSPRNG for the
  *key* and, separately, a durable, monotonic, never-reset counter for the
  *nonce* — a strictly harder operational problem, because the counter
  must survive process restarts, crashes, and (per
  `docs/anti_analysis_shadow_vault_risks.md` §3) VM/container snapshot
  restores without ever going backward or repeating.
- This codebase has **no durable local storage of any kind implemented
  yet** (`docs/implementation_readiness_checklist.md` §2 — `StorageBackend`
  is still a skeleton). A counter-nonce scheme would require solving
  durable, crash-safe, snapshot-safe counter persistence FIRST, which is
  strictly more machinery than this Implementation Phase's early stages
  (`docs/implementation_phase_roadmap.md` §1 items 1–6) are scoped to
  introduce.

## 6. MVP decision: random nonce, drawn from the CSPRNG

- **For the MVP crypto core, this codebase uses a CSPRNG-drawn random
  nonce, not a counter.** This follows directly from §5: this codebase has
  no durable, crash-safe counter-persistence mechanism today, and building
  one is a strictly larger and separate undertaking than implementing
  `randomBytes` itself.
- The nonce is drawn from the **same CSPRNG source `randomBytes` uses**
  once real (`getrandom`, per `docs/public_random_design.md` §6 step 4:
  "Implement real nonce generation for the AEAD path, consuming the same
  `getrandom` call `randomBytes` uses") — never a second, independent
  entropy source, and never a deterministic derivation from any other
  value.
- **A counter-nonce scheme remains a possible FUTURE optimization**
  (e.g. paired with an already-durable, already-reviewed local-storage
  counter, once one exists) but is explicitly out of scope for the first
  real AEAD implementation. Adopting one later is its own explicitly-
  reviewed stage, not a silent upgrade.

## 7. Deterministic nonce generation is forbidden

- **No nonce may ever be computed deterministically from public or
  predictable inputs** — not a message counter without durable, crash-safe
  persistence (§5, §6), not a timestamp, not a hash of the plaintext or
  AAD, not a fixed or all-zero value, and not any combination of these
  used as a substitute for a real CSPRNG draw.
- **This includes "cleverly" deriving a nonce from something that looks
  random but is not drawn from a CSPRNG** — e.g. hashing a request id or a
  sequence number is still deterministic and still forbidden, even though
  the output looks like random bytes.
- Rationale: a deterministic nonce is either fully predictable (defeating
  any confidentiality benefit a fresh nonce provides against certain
  attacks) or silently becomes a de facto counter with none of a real
  counter's durability/monotonicity guarantees (§5) — the worst of both
  approaches.

## 8. Nonce derived from seed / password / user id is forbidden

- **A nonce must never be derived from a seed, mnemonic, passphrase,
  Apple/Google/WebAuthn identifier, Nostr pubkey, or any other stable
  per-user or per-account value.** This is the nonce-specific instance of
  the same rule `docs/vault_crypto_identity.md` §1 and
  `docs/crypto_test_vectors.md` §9 already fix for KEYS ("Apple / Google /
  WebAuthn credential as a seed" is forbidden) — a nonce derived from a
  stable identifier is itself a form of key/identity-derived material and
  inherits the same problems: it is not secret, it does not rotate
  independently, and reusing the same underlying identifier across
  multiple encryption operations reintroduces exactly the (key, nonce)
  collision risk §2 forbids, just relabeled as "derivation" instead of
  "reuse."
- **A user id, device id, or session id is not an acceptable nonce
  component** even when concatenated with other data or combined with a
  counter, because none of these values carries a uniqueness guarantee
  strong enough to substitute for either a CSPRNG draw (§6) or a real
  durable counter (§5).

## 9. A nonce is not a secret, but reuse is still forbidden

- **A nonce carries no confidentiality requirement of its own** — per RFC
  8439/NIST SP 800-38D and this crate's own test-vector plan
  (`docs/crypto_test_vectors.md` §4), the nonce is an explicit input to
  both seal and open and is expected to travel alongside the ciphertext.
  It does not need `zeroize`, `secrecy`, or any of the secret-handling
  machinery `docs/secret_lifecycle_implementation_plan.md` fixes for real
  keys.
- **This does NOT relax the reuse prohibition (§2).** "Not secret" and
  "must never repeat under the same key" are independent properties — a
  nonce can be public knowledge and still be catastrophic to reuse. Do not
  read §9's first bullet as license to treat nonce generation casually.

## 10. Nonce storage and transmission policy

- **A nonce travels with its ciphertext, in the clear, as a matter of
  course** — this is the standard AEAD usage pattern this crate's own
  vector plan already assumes (`docs/crypto_test_vectors.md` §4 lists
  nonce as one of the fixed, non-secret vector fields alongside plaintext
  and AAD).
- **A nonce is never logged as a value on its own outside of the
  ciphertext it belongs to** in any context that could separate it from
  its key/ciphertext pairing without also recording which key it belongs
  to — not because the nonce is secret, but because an orphaned nonce
  value with no linkage to its key cannot later be checked for reuse.
  This is a forward-looking hygiene rule for whatever future audit
  mechanism might exist (`docs/fedos_core_public_api_design.md` §9: "no
  audit record may contain a ... nonce ... byte" already forbids this
  outright for the audit path specifically).
- **No caller-facing function accepts or returns a nonce as a standalone
  parameter.** Per `docs/public_random_boundary.md` §3, nonce generation
  is consumed ONLY internally by the future `encrypt` implementation —
  never exposed as its own public function a caller could invoke and then
  reuse the output of. `decrypt` receives whatever nonce representation
  the ciphertext's own wire format carries (a format not yet fixed — see
  `docs/implementation_readiness_checklist.md` §2, "no encrypted packet
  format exists").

## 11. Failure-time handling

- **A CSPRNG failure while drawing a nonce MUST abort the encrypt
  operation entirely — it must never fall back to a deterministic, zero,
  reused, or otherwise degraded nonce.** This follows directly from §7's
  prohibition: there is no acceptable fallback nonce, so a failure to draw
  one is not a degraded-mode case, it is a hard failure of the whole
  `encrypt` call.
- **The failure surfaces through the same fixed error taxonomy**
  `docs/fedos_core_public_api_design.md` §8 already requires for the
  public API generally (a closed label set, never raw platform error
  text) — see `docs/random_bytes_implementation_plan.md` §6 for the
  specific CSPRNG-failure label this maps onto.
- **A failed encrypt operation must not leave a partially-written
  ciphertext, partially-advanced state, or a leaked plaintext.** This
  restates `docs/vault_crypto_identity.md` §3's "failed tag = reject, do
  not fall back to plaintext" in the nonce-specific case: if the nonce
  step fails, the operation never proceeds to actually encrypt anything.

## 12. Test policy

- **No test may demonstrate nonce reuse "working."**
  `docs/crypto_test_vectors.md` §4 already fixes this as a required
  negative-vector rule; this document restates it as binding on any future
  test suite specifically for the nonce-generation code path itself (not
  only the AEAD vector suite): a test asserting "two encrypts with the
  same nonce produce different ciphertexts" (or similar) must not exist,
  because it would document reuse as a supported pattern rather than a
  forbidden one.
- **A deterministic/seeded test RNG is permitted ONLY inside `#[cfg(test)]`
  and must never be reachable from a production code path** — the same
  separation `docs/fedos_core_rust_safety.md` §7 already requires
  ("Separate test RNG from production RNG... a deterministic RNG never
  reaches a production code path") and that
  `docs/random_bytes_implementation_plan.md` §8 restates for `randomBytes`
  specifically. A future nonce-generation unit test may use a fixed,
  labeled test nonce to check wire-format plumbing (e.g. "does the
  ciphertext carry the nonce bytes it was given"), but such a test must be
  clearly test-only and must never be mistaken for, or reused as, a
  production nonce path.
- **A future reuse-detection test, if one is ever added, tests the
  ABSENCE of reuse under realistic operation counts** — e.g. drawing many
  nonces from the real (or a `cfg(test)`-only mirror of the real) CSPRNG
  path and asserting no collision — never a test that constructs a reused
  nonce by hand and asserts the encrypt call "worked anyway."

## 13. Relationship to a future NIP-44 implementation

- **NIP-44 is not implemented anywhere in this codebase** (confirmed
  directly: `docs/boundary_phase_index.md` §2, `docs/crypto_test_vectors.md`
  §7 — "nothing encrypts or decrypts NIP-44 payloads today"). This policy
  does not implement it either.
- **NIP-44's own nonce is per-message and part of its versioned wire
  format**, per `docs/crypto_test_vectors.md` §7 ("Each vector fixes:
  conversation key ... nonce (per-message), plaintext payload, and
  expected payload"). A future NIP-44 implementation would need to follow
  NIP-44's own upstream-specified nonce construction exactly (verified
  against the upstream `nostr-protocol/nips` NIP-44 vectors), which may
  or may not match this document's §6 MVP choice for this crate's OWN
  general-purpose AEAD boundary byte-for-byte — NIP-44 conformance takes
  precedence over this document's general policy for NIP-44 traffic
  specifically, since NIP-44 vectors define correctness for that wire
  format, not this document.
- **Regardless of which nonce construction a future NIP-44 stage uses,
  §2's reuse prohibition and §7's determinism prohibition apply
  unconditionally** — NIP-44 conformance can change HOW a nonce is shaped
  and sourced for that specific wire format, it can never justify reusing
  one or deriving one deterministically from public/predictable input.
- Building NIP-44 remains its own, separate, future, explicitly-reviewed
  stage (`docs/crypto_test_vectors.md` §2 lists it as in-scope for the
  vector plan but not for any implementation stage today) — nothing in
  this document schedules or authorizes starting it.

## 14. What this document does NOT do

- Does not generate a single nonce byte anywhere.
- Does not change `FedosNonceBoundary`/`fedos_nonce_boundary_status()`
  (Stage 103) or any other type in `packages/fedos-core-rust/src/lib.rs`.
- Does not adopt XChaCha20-Poly1305 or any new dependency.
- Does not implement a durable counter, a wire format, or a public nonce
  parameter of any kind.
- Does not implement NIP-44 or its nonce construction.
- Does not touch `src/`, `packages/`, `Cargo.toml`, or `test/`.

## 15. Conclusion

- **Nonce reuse under a key is forbidden, unconditionally, for every AEAD
  candidate this crate has adopted (ChaCha20-Poly1305, AES-256-GCM) or
  might adopt (XChaCha20-Poly1305) or interoperate with (NIP-44).**
- **The MVP nonce source is a CSPRNG-drawn random nonce**, not a counter,
  because this codebase has no durable crash-safe counter-persistence
  mechanism today and building one is a separate, larger undertaking.
- **Deterministic and identity/seed-derived nonces are forbidden outright**
  — there is no acceptable fallback nonce, including on CSPRNG failure,
  which must abort the operation instead.
- **A nonce is not secret but must never be exposed as a standalone
  public function output or reused across encrypt calls under the same
  key.**
- This policy is now fixed for any future stage that implements real AEAD
  — the next Implementation Phase step
  (`docs/implementation_phase_roadmap.md` §1 item 2) is the Rust
  `randomBytes` implementation itself, which this nonce policy was
  written to precede.

## 16. Stage 138 update — first implementation against this policy

- **`fedos_aead_nonce_96()`** (`packages/fedos-core-rust/src/lib.rs`,
  Stage 138) is the first code anywhere in this codebase to draw a real
  nonce, and it implements §6's MVP decision exactly: a CSPRNG-drawn
  random nonce via `getrandom::fill`, fixed at 96 bits
  (`FedosAeadNonceKind::NinetySixBit`, `[u8; 12]`) — matching both
  currently-adopted AEAD candidates' shared nonce size (§3, §4).
- **§7's determinism prohibition and §8's seed/password/user-id
  prohibition hold exactly as fixed** — `fedos_aead_nonce_96` accepts no
  parameter of any kind (no length, no seed, no password, no user id, no
  counter), and never derives its output from anything but the OS CSPRNG.
- **§11's failure-time handling holds exactly as fixed** — a CSPRNG
  failure returns a fixed `FedosNonceState::EntropySourceUnavailable`
  with `nonce: None`; there is no fallback PRNG and no panic.
- **§10's "never a standalone public function" framing is intentionally
  NOT what this stage does** — `fedos_aead_nonce_96` IS a standalone
  public function (unlike the internal-only design §10 originally
  sketched), because no AEAD `encrypt` implementation exists yet for it
  to be internal to. It is documented, both in code and in
  `test/fedos_core_rust_aead_nonce.test.ts`, as NOT connected to any
  encrypt/decrypt/AEAD function — a future AEAD implementation stage
  would need to be the one to call it, and that wiring does not exist
  yet. This is a deliberate, reviewed sequencing choice (helper before
  consumer), not a reopening of §10's policy.
- **Still not implemented**: any AEAD seal/open, any connection to
  `SecretHandle`/`aead_core`/`kdf_core`, any Runtime/Worker/WASM wiring,
  and NIP-44 (§13 stands unchanged).

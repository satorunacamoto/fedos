## 3. Inventory of existing production crypto primitives (read-only, this worktree)

- **secp256k1/ECDH**: `packages/fedos-core-rust/src/crypto/conversation_key.rs`, `derive_conversation_key_via_ecdh_internal(secret_key: &SecretHandle, public_key: &SecretHandle) -> ConversationKeyDecision`. Manual `k256` point math: x-only 32-byte public key lifted to a point via SEC1-compressed-even-Y convention (`0x02` prefix) + `AffinePoint::from_encoded_point` (rejects off-curve/malformed input, never panics), scalar multiplication, X-coordinate extracted as the raw shared secret, THEN immediately baked into `Hkdf::<Sha256>::extract(Some(b"nip44-v2"), &shared_x)` — the NIP-44-specific salt is inseparable from this function. **Verdict: the point-validation/ECDH-math technique is directly reusable; the function itself is NOT** — its baked-in `"nip44-v2"` salt would silently mix an unrelated HKDF domain into ratchet root-key derivation, which Phase D explicitly forbids. This Arc adds a new, narrow, structurally-parallel function performing the SAME validated ECDH math, returning the raw shared secret for the ratchet's OWN root KDF to consume — never modifying `conversation_key.rs`.
- **Ephemeral keypair generation**: no existing "generate a fresh random keypair" primitive — every existing key in this crate is deterministic-from-Master-Seed. The reusable pieces are `fedos_random_bytes_32()` (`lib.rs`, real `getrandom`-backed CSPRNG, confirmed non-placeholder) for entropy, and the scalar→point technique from `derive_nostr_public_key_internal` (`lib.rs`, `SecretKey::from_slice` → `to_encoded_point(true)` → x-only 32 bytes) for the public-key half. This Arc composes these two into a new `generate_direct_ratchet_keypair_internal()` — the one new CSPRNG-consuming primitive this Arc adds.

## 4. Design decisions this report locks in before any production edit

- **Root/Chain KDF do not use the shared `HkdfDomain` fixed-domain machinery.** Both operate on ALREADY-high-entropy accumulated secret material (the current root/chain key), exactly analogous to the Foundation Arc's own second-stage `Hkdf::from_prk(...).expand(context, ...)` step in `fedos_derive_direct_ratchet_session_sealing_key_internal` — which deliberately bypassed the shared fixed-domain helper because that helper never accepts caller-supplied context. This Arc follows the identical, already-accepted precedent: raw `hkdf::Hkdf<Sha256>` calls with fixed, compile-time domain-separation label CONSTANTS (never caller-supplied), zero new `HkdfDomain` variants.
- **The very first root key is bootstrapped from the existing, real `resolve_conversation_key()` output**, per the review's own §4 of `08_dh_session_ratchet.md` ("the existing static ECDH is a reasonable, already-real seed for session bootstrap"). A narrow new accessor exposes the already-computed `AeadKeyHandle`'s underlying 32 bytes for this ONE reviewed purpose (ratchet bootstrap), mirroring the "one accessor per reviewed caller" convention.
- **Raw secret bytes never cross the WASM boundary.** The Ratchet Session's own Rust struct holds an internal reference/parameter to the SAME `FedosMasterSeedAuthority` instance the caller already owns, and calls its EXISTING `seal_direct_ratchet_secret`/`restore_direct_ratchet_secret` methods internally (Rust-to-Rust) to produce/consume opaque sealed-blob STRINGS only — the WASM/TypeScript boundary only ever sees session handles, opaque ciphertext, and opaque sealed-blob strings, exactly matching Phase N/O's prohibitions.
- **Message authentication is AEAD-only** — the header travels as AAD bound to the ciphertext; no separate HMAC layer is added (NIP-44's own separate HMAC is a legacy wire-format requirement this Arc's fresh internal format does not inherit).
- **Nonce strategy**: fixed (all-zero, 12-byte) AEAD nonce for message encryption. Cryptographically sound BECAUSE each derived message key is used to seal exactly one message, ever, then is discarded — key-uniqueness alone (not nonce variation) provides AEAD safety here, the same property real Double Ratchet designs rely on. Documented explicitly in the suite construction document (Phase B) as a deliberate, justified departure from "fresh random nonce per encryption" (which the Conversation-level static-key encryption still correctly requires, since THAT key is reused across many messages).
- **Suite identifier**: reuses the EXISTING `FedosDirectRatchetSuite = "fedos-direct-ratchet-v1"` literal already defined in the Foundation Arc — no new suite type, no version bump.

No production edits precede this report.

# Secure Runtime Alpha 3161–3240: Account-to-Device Signature Verification Boundary — Execution Spec

Architecture frozen. This Arc redesigns nothing: no change to `src/sync/`, `src/device/fedos_device_binding.ts`'s own trust vocabulary/transition table, `src/device/persistence/` (Alpha 2921–3000's Device Registry), Conversation Runtime, Archive, Search, Sender-Key, or Desktop Shell; no new Rust/WASM primitive; no new dependency. It closes the exact blocker Alpha 2921–3000 named: no accepted cryptographic boundary proved that an account authorizes a particular independent Device key.

Base revision: worktree `C:\wt\account-device-signature`, branch `arc/account-device-signature-boundary`, based on `master` tip `cb6a666` (Secure Runtime Alpha 2921–3000, "Device Trust and Multi-Device Runtime Integration"), which already contains the Master Seed Authority, account-index-derived Nostr identities, the existing Nostr signing authority, `FedosDeviceBindingV1`, the Device Registry, Device trust-state transitions, and `UnavailableFedosDeviceRegistrationAuthority`, and the `docs/reviews/multi_device_device_trust_v1` review (commit `4672244`).

## Phase A — Source reconciliation (verified against real source)

1. **Account identity derivation**: `src/runtime/master_seed/` (`FedosWasmMasterSeedAuthority`) holds the one Master Seed; account-index-derived Nostr identities come from the WASM boundary, never re-derived in TypeScript.
2. **Account public-key retrieval**: `FedosNostrSigningAuthority.publicIdentityForAccount(accountIndex)` (`src/nostr/sign/fedos_nostr_signing_authority.ts`) — derives a `FedosNostrSigningPublicIdentity { accountIndex, publicKeyHex }` WITHOUT signing anything; `null` when no Master Seed is held. Production implementation: `FedosWasmNostrSigningAuthority`.
3. **Account signing operations**: `FedosNostrSigningAuthority.signEvent(request: FedosNostrUnsignedEventRequest)` — `kind` is FIXED to `1` by Alpha 424's own reviewed scope decision, enforced at both the TypeScript boundary (`isWellFormedFedosNostrUnsignedEventRequest`) and the Rust/WASM boundary (`sign_nostr_event`). No caller-supplied `pubkey`/`id`/`sig` field exists anywhere on the request type. This Arc does NOT widen this API — no new kind, no new WASM export.
4. **Existing signature verification**: `NobleSignatureVerifier` (`src/nostr/noble_signature.ts`) — real BIP-340 Schnorr over secp256k1 via `@noble/curves`, already a production dependency. Recomputes the NIP-01 event id (`src/nostr/event.ts`'s `serializeForId`) and checks `schnorr.verify`. Reused verbatim by this Arc's account-authorization verifier; no new cryptographic primitive added.
5. **Device ID generation**: `deviceId` remains a caller-/Runtime-supplied stable string (Alpha 2921–3000's own model, unchanged) — this Arc does not generate device ids.
6. **Device public-key representation (before this Arc)**: `FedosDeviceBindingV1.devicePublicKeyRef` — an OPAQUE, nullable string reference, always `null` when `trustState === "unavailable"`. No independent Device key authority existed to populate it with a real value.
7. **Independent Device-key authority (before this Arc)**: none. `src/crypto/types.ts` remains an unchanged placeholder seam — confirmed unmodified by this Arc.
8. **Device Binding schema**: `FedosDeviceBindingV1` (`src/device/fedos_device_binding.ts`) — `schemaVersion: 1`, `deviceId`, `accountRef {authority, publicIdentifier, identityId}`, `devicePublicKeyRef` (opaque, nullable), `label`, `createdAt`, `trustState: "pending"|"trusted"|"revoked"|"unavailable"`, `capabilityVersion: 1`, `revokedAt`. Closed transition table: `pending -> {trusted, revoked}`, `trusted -> {revoked}`, `unavailable -> {revoked}`, `revoked -> {}` (terminal). Unmodified by this Arc.
9. **Device Registration authority interface**: `FedosDeviceRegistrationAuthority` (`src/device/fedos_device_registration_authority.ts`) — `authorizeRegistration`/`authorizeTrustConfirmation`, each returning `{allowed, capability: "verified"|"unavailable", reason}`. Unmodified port; this Arc adds a NEW, second production adapter (`AlreadyVerifiedFedosDeviceRegistrationAuthority`) alongside the existing `UnavailableFedosDeviceRegistrationAuthority` — it does not replace or widen the port.
10. **Device Registry write behavior**: `PersistedFedosDeviceTrustAuthority` (`src/device/persistence/persisted_fedos_device_trust_authority.ts`) — `registerDevice`/`confirmTrust`/`revokeDevice`, event-sourced through `FedosDeviceRegistryPersistence` (codec + in-memory + append-only backends, fail-closed on corruption). Unmodified; this Arc's orchestrator is a NEW caller, constructing its OWN private instance.
11. **Revocation semantics**: `revokeFedosDeviceBinding` — terminal, no outgoing edge from `"revoked"` in `fedos_device_binding.ts`'s own transition table. Unmodified.
12. **Blocker reproduction (before this Arc's own new files)**: `UnavailableFedosDeviceRegistrationAuthority.authorizeTrustConfirmation()` always returns `allowed: false, capability: "unavailable"` — no device could ever reach `"trusted"` in production.
13. **Expected files to change**: a new `src/device/crypto/` (Device signing keypair), a new `src/device/binding_challenge/` (canonical challenge, account authorization, device proof, the real registration authority orchestrator, the internal `AlreadyVerifiedFedosDeviceRegistrationAuthority`, and the Phase J factory), a new replay-persistence sub-tree under `src/device/persistence/` (codec, port, in-memory, append-only). `src/sync/`, `src/device/fedos_device_binding.ts`, `src/device/persistence/persisted_fedos_device_trust_authority.ts`, `src/device/unavailable_fedos_device_registration_authority.ts`, Conversation Runtime, Archive, Search, Sender-Key, and the Desktop Runtime/Shell are all byte-for-byte unmodified.
14. **Baseline failures**: `npm run typecheck` clean except the one pre-existing, unrelated `test/secure_runtime_alpha_477_scheduler_lifecycle_model.test.ts:121` error (confirmed present in the primary, non-worktree checkout at the same line — not this Arc's own change, already named by every recent completion declaration).
15. **Threat/data-flow diagram**:

```
account Master Seed (WASM, never leaves boundary)
    -> FedosNostrSigningAuthority.signEvent(kind=1, content=canonical challenge)
    -> FedosDeviceBindingAccountAuthorizationV1 { challenge, event }
                                                              \
Device signing keypair (in-process, CSPRNG, never persisted)  \
    -> FedosDeviceSigningKeypair.sign(sha256(prefix || canonical challenge))
    -> FedosDeviceBindingProofOfPossessionV1 { challenge, devicePublicKeyHex, signatureHex }
                                                              /
                            both -> FedosDeviceBindingRegistrationAuthority.registerDevice()
                                    1. re-verify account signature (NobleSignatureVerifier)
                                    2. re-verify device signature (verifyFedosDeviceSigningSignature)
                                    3. replay/expiry check (FedosDeviceBindingChallengeReplayPersistence)
                                    4. PersistedFedosDeviceTrustAuthority.registerDevice() + confirmTrust()
                                    -> FedosDeviceBindingV1 { trustState: "trusted", devicePublicKeyRef }
```

An attacker controlling only the account key cannot register a Device key they do not hold (Device proof independently re-verified). An attacker controlling only a Device key cannot self-authorize under someone else's account (account authorization independently re-verified). An attacker who intercepts one signed request cannot replay it after the Registry already consumed its nonce (`"replayed"`), nor after it expires (`"expired"`), nor against a different device/action/account (content-mismatch at the crypto layer, or `"unsupported"` at the orchestrator layer).

## Phase B — Device Key Authority

Compared: **A.** independent random Device key via reviewed CSPRNG — **ADOPTED**. **B.** deterministic key derived from the Master Seed — REJECTED (not independent; compromise of one derives the other, contradicts the review's own "account identity + independent device keys" recommendation). **C.** reuse the account signing key as the Device key — REJECTED (explicit prohibition; also collapses the two-signature security property this Arc exists to build). **D.** caller-provided raw private key — REJECTED (`FedosDeviceSigningKeypair` has no constructor accepting external key bytes; the only producer is `generateFedosDeviceSigningKeypair()`).

`src/device/crypto/fedos_device_signing_keypair.ts` reuses `@noble/curves` (already a production dependency, already used for Nostr Schnorr verification) and `@noble/hashes/utils.js`'s `randomBytes`-backed CSPRNG (already this codebase's own established id-generation primitive) — no new dependency. `FedosDeviceSigningKeypair` is an opaque handle: the secret key lives in one private class field, is never returned by any method, and is used only inside `sign()`. Process-memory-only — this Arc implements no durable storage for a Device's own secret key (named explicitly in the Security Statement below).

## Phase C — Versioned Binding Challenge

`src/device/binding_challenge/fedos_device_binding_challenge.ts`. `FedosDeviceBindingChallengeV1`: `schemaVersion: 1`, `domain` (fixed constant `"fedos:device-binding:v1"`), `action: "register-device"|"revoke-device"`, `deviceId`, `devicePublicKeyHex`, `issuedAt`, `expiresAt` (strictly `> issuedAt`), `nonce` (16-byte CSPRNG hex, the replay key). Canonical serialization is a fixed-order JSON array tuple (`[domain, schemaVersion, action, deviceId, devicePublicKeyHex, issuedAt, expiresAt, nonce]`), mirroring `src/nostr/event.ts`'s own `serializeForId()` convention — no canonical-JSON dependency needed, no object-key-ordering ambiguity. `domain` is never caller-supplied and is checked both structurally (`isWellFormedFedosDeviceBindingChallengeV1`) and at every verification call site, preventing cross-protocol signature reuse. `action` is part of the signed content, so a `"register-device"` challenge can never be replayed to authorize a `"revoke-device"` action.

**Bug found and fixed during Phase K test-writing**: `isWellFormedFedosDeviceBindingChallengeV1`'s own field-count guard checked `keys.length !== 7`, but the interface has 8 fields (`schemaVersion, domain, action, deviceId, devicePublicKeyHex, issuedAt, expiresAt, nonce`). This made the validator reject every real, well-formed challenge unconditionally — caught immediately by the first real-crypto test in this Arc's own suite (`authorizeFedosDeviceBindingChallenge` returning `null` for a genuinely valid challenge), fixed to `keys.length !== 8` in the same commit. No other file depended on the broken behavior (nothing had exercised this path with a real object before this Arc's own tests existed).

## Phase D — Account Authorization Signature

`src/device/binding_challenge/fedos_device_binding_account_authorization.ts`. Source inspection (Phase A) confirmed `kind: 1` is a deliberate, reviewed, unchanged Alpha 424 scope boundary — not an accepted place to add a second signing mode. Decision: **detached, domain-specific authorization inside an ordinary kind-1 event**, not a widened signing API. The challenge's own canonical serialization becomes the `content` of a kind-1 event tagged `["t", "fedos-device-binding-v1"]` (a non-authenticating marker — the real security boundary is `domain` inside the signed content). `authorizeFedosDeviceBindingChallenge(signingAuthority, accountIndex, challenge)` signs; `verifyFedosDeviceBindingAccountAuthorization(authorization, now)` verifies end-to-end: structural well-formedness -> domain check -> kind check -> exact tag+content reconstruction -> real `NobleSignatureVerifier.verify()` -> expiry. The account's public identity (`accountPublicKeyHex`) is read ONLY from the cryptographically-verified `event.pubkey` after signature verification succeeds — never a caller claim, populated only on outcome `"valid"`.

Verified requirements (Phase K tests): wrong account signature fails (`"invalid-signature"`); changed `deviceId`/`devicePublicKeyHex`/`action`/`expiresAt`/`nonce` after signing all fail (`"content-mismatch"`, since the reconstructed canonical content no longer matches what was actually signed); expired fails (`"expired"`); a real signature produced for unrelated kind-1 content can never be repurposed as an authorization (`"content-mismatch"` — cross-domain/cross-purpose replay denied).

## Phase E — Device Proof of Possession

`src/device/binding_challenge/fedos_device_binding_proof_of_possession.ts`. The Device signs `sha256("fedos-device-binding-proof-of-possession-v1:" + canonicalChallenge)` — a FIXED preimage prefix distinct from the account authorization's own Nostr-event preimage, so the two signature roles can never be confused or substituted for each other. `createFedosDeviceBindingProofOfPossession(keypair, challenge)` returns `null` if `keypair.publicKeyHex !== challenge.devicePublicKeyHex` — a Device can never prove possession of a key it does not hold, even one it merely claims to via the challenge's own `devicePublicKeyHex` field. Pure, synchronous, side-effect-free — never touches an account identity, the Registry, or any persistence by itself. Account authorization alone cannot register an arbitrary unowned Device key (the orchestrator, Phase G, independently re-verifies the Device proof on every call); Device proof alone cannot self-authorize an account (the orchestrator independently re-verifies the account authorization on every call). Both are required, unconditionally, before `FedosDeviceBindingRegistrationAuthority.registerDevice()` ever calls into the Registry — no intermediate single-proof `"pending"` state is ever created by this Arc's own orchestrator (Alpha 2921–3000's pre-existing `"pending"` state remains reachable only through the legacy `UnavailableFedosDeviceRegistrationAuthority` path, which this Arc does not touch).

## Phase F — Replay and Expiry

`src/device/persistence/` gains a deliberately separate replay-persistence sub-tree — `fedos_persisted_device_binding_challenge_consumption_v1.ts` (the record: `nonce, domain, action, deviceId, devicePublicKeyHex, accountAuthority, accountPublicIdentifier, consumedAt, outcomeSummary`), `fedos_device_binding_challenge_replay_persistence.ts` (port), `fedos_device_binding_challenge_replay_codec.ts` (fails closed to `null` on any malformed/off-schema/extra-field record), `in_memory_fedos_device_binding_challenge_replay_persistence.ts`, `append_only_fedos_device_binding_challenge_replay_persistence.ts` (NDJSON, insert-only, one corrupt or unparseable line throws unconditionally — mirrors the Device Registry's own append-only discipline exactly). A separate file tree and port from the Device Registry itself (Phase F/I's own explicit instruction) — never overloads the Sync Journal.

The orchestrator (Phase G) checks replay BEFORE mutating the Registry: `getConsumption(nonce)` — absent means fresh; present with byte-identical content-defining fields (`domain, action, deviceId, devicePublicKeyHex, accountAuthority, accountPublicIdentifier`) means idempotent (the SAME previously-recorded outcome is returned, the Registry is not touched again); present with ANY different field means `"replayed"` (denied). This is a single-writer, in-process guard (Node's own single-threaded execution model) — it makes no distributed exactly-once claim, stated honestly here and in the Security Statement. Restart-safety is proven directly: a fresh `AppendOnlyFedosDeviceBindingChallengeReplayPersistence` instance constructed over the same file path after a simulated restart still reports a previously consumed nonce.

## Phase G — Real Registration Authority

`src/device/binding_challenge/fedos_device_binding_registration_authority.ts` — `FedosDeviceBindingRegistrationAuthority`. Owns a PRIVATE `PersistedFedosDeviceTrustAuthority` instance constructed internally with `AlreadyVerifiedFedosDeviceRegistrationAuthority` (`./fedos_already_verified_device_registration_authority.ts`) — never exposed to any caller, never constructed anywhere else with that authority. "Verified" is never a default; it is a fact this file itself establishes on every call, before ever touching the Registry: (1) validate challenge structure + `action === "register-device"`, (2) verify the account authorization is over the EXACT same canonical challenge the Device proof also covers (byte-for-byte serialization equality, not merely a shared `nonce`), (3) re-verify the account signature, (4) re-verify the Device proof, (5) check replay/expiry, (6) call `PersistedFedosDeviceTrustAuthority.registerDevice()` then `confirmTrust()` in the same call — trusted registration is a single orchestrator call, not a separate later step, because both required proofs are already in hand.

Outcome vocabulary (this repo's own coarse-result convention): `"registered-trusted" | "already-present" | "conflict" | "invalid-account-proof" | "invalid-device-proof" | "expired" | "replayed" | "revoked" | "unsupported" | "failed"`. A pre-existing binding not currently `"pending"` (e.g. one created by the legacy `UnavailableFedosDeviceRegistrationAuthority` path and stuck at `"unavailable"`) has no upgrade path through this Arc's orchestrator — mapped to `"unsupported"`, a documented limitation rather than a silent failure: a genuinely-owned device re-registers under a NEW `deviceId`, matching this codebase's own "revoked/blocked ids are not reused" model. `"revoked"` is never mutated back to `"trusted"` — `PersistedFedosDeviceTrustAuthority`'s own transition table has no such edge, and this orchestrator adds no bypass.

## Phase H — Revocation Authorization

`FedosDeviceBindingRegistrationAuthority.revokeDevice(accountAuthorization, now)` — implemented, account-authorization-only (no Device cooperation required or possible, since a lost/stolen/compromised Device cannot be trusted to help revoke itself). Uses the SEPARATE `action: "revoke-device"` (distinct signed content from `"register-device"`, so a registration authorization can never be replayed as a revocation or vice versa). Bound to the exact target binding via BOTH `deviceId` AND `devicePublicKeyHex` (the challenge must name the currently-bound key, not just the device id). Outcome vocabulary: `"revoked" | "already-revoked" | "not-found" | "wrong-account" | "device-mismatch" | "invalid-account-proof" | "expired" | "replayed" | "unsupported" | "failed"`. Duplicate revocation is idempotent (`"already-revoked"`); wrong-account revocation is denied (`"wrong-account"`) without mutating the binding; a revoked binding can never authorize its own reinstatement (revocation is terminal at the `fedos_device_binding.ts` layer this orchestrator has no bypass for). No remote-erasure claim of any kind is made — see the Security Statement. No device-sync key rotation is implemented.

## Phase I — Persistence

Uses the EXISTING Device Registry persistence (`PersistedFedosDeviceTrustAuthority` + `FedosDeviceRegistryPersistence`, Alpha 2921–3000, unmodified) for the Device Binding itself. Adds the SEPARATE replay-consumption persistence described in Phase F, because a consumed-challenge fact is not a Device Binding fact and the existing event model has no field for it. Both provide: versioned codec (fails closed to `null`), in-memory backend, append-only backend (fails closed on corruption — one bad line throws unconditionally), identical-duplicate ("already-present") vs conflicting-duplicate ("conflict") behavior, and restart recovery (a fresh instance over the same log file replays it deterministically). No private key or Master Seed field exists in either the Device Binding record or the replay-consumption record — verified directly by test (Phase K, items 24–26), not merely asserted.

## Phase J — Factory/Adapter Boundary

`src/device/binding_challenge/fedos_device_binding_boundary_factory.ts` — `createFedosDeviceBindingBoundary(deps)`. Accepts `registryPersistence`, `replayPersistence`, an optional injected clock (`now`, defaults to wall-clock seconds), an optional injected nonce authority (defaults to the reviewed CSPRNG generator — never `Math.random()`), and explicit operational limits (`challengeTtlSeconds`, default 300). Returns `{ registrationAuthority, mintChallenge }` — the ONE construction point a future Desktop Runtime integration step would call. **Not wired into `fedos_desktop_runtime.ts` in this Arc** (Parallel Safety — this Arc must remain independently mergeable alongside the Desktop Content Accessor Arc).

**Documented future integration step** (not performed by this Arc): `FedosDesktopRuntimeConfig` would gain one opt-in flag (mirroring `deviceTrustEnabled`'s exact discipline — e.g. `deviceBindingEnabled?`) plus the file path(s) for the replay-persistence log; `FedosRunningDesktopRuntime` would gain one narrow `deviceBinding()` accessor that calls `createFedosDeviceBindingBoundary()` exactly once at Runtime start, mirroring `deviceTrust()`'s own "one instance per running runtime, no global singleton, throws once stopped" contract precisely. That accessor would sit ALONGSIDE the existing `deviceTrust()` accessor (which stays wired to the legacy `UnavailableFedosDeviceRegistrationAuthority` path for any caller not yet using real signatures) — never replacing it in this Arc or the one after it, since removing the legacy accessor is itself a scope decision for a future, explicitly-scoped Arc. No alternative parallel authority tree exists anywhere in this Arc: the factory's own `FedosDeviceBindingRegistrationAuthority` is the same class, same file, used directly by every test.

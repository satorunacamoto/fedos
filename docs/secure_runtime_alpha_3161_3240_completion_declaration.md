# Secure Runtime Alpha 3161–3240: Account-to-Device Signature Verification Boundary — Completion Declaration

## What this Arc proves

- A real, independent Device signing keypair exists (`src/device/crypto/fedos_device_signing_keypair.ts`), generated by a reviewed CSPRNG (`@noble/curves`'s own `schnorr.utils.randomSecretKey()`, backed by `@noble/hashes`), never derived from the Master Seed, never the account signing key, an opaque handle with no raw private-key getter anywhere in the file (verified directly — `Object.getOwnPropertyNames` on a live instance carries no `secret`/`private`-named field).
- A canonical, versioned, domain-bound `FedosDeviceBindingChallengeV1` exists (`src/device/binding_challenge/fedos_device_binding_challenge.ts`) — fixed domain separator, fixed-order array canonical serialization, `register-device`/`revoke-device` action, expiry strictly after issuance, CSPRNG nonce as the replay key.
- The account produces a real, independently verifiable authorization signature over the complete canonical challenge (`fedos_device_binding_account_authorization.ts`), reusing the EXISTING kind-1 Nostr signing authority unwidened, verified with the EXISTING, unmodified `NobleSignatureVerifier` (real BIP-340 Schnorr). The account's public identity is read only from the cryptographically-verified `event.pubkey`, never a caller claim.
- The Device produces a real proof of possession of its own signing key (`fedos_device_binding_proof_of_possession.ts`), over a digest with a fixed preimage prefix distinct from the account's own signing preimage — the two signature roles can never be confused or substituted.
- A real `FedosDeviceBindingRegistrationAuthority` (`fedos_device_binding_registration_authority.ts`) independently re-verifies BOTH signatures on every call — account authorization alone can never register an arbitrary unowned Device key; Device proof alone can never self-authorize an account — before ever touching the EXISTING, unmodified Device Registry (`PersistedFedosDeviceTrustAuthority`, Alpha 2921–3000), through an internal `AlreadyVerifiedFedosDeviceRegistrationAuthority` this orchestrator is the ONLY caller of anywhere in `src/`.
- A durable, restart-safe replay/expiry guard exists, separate from the Device Registry's own persistence (codec, in-memory + append-only backends, fail-closed on corruption) — proven directly: a fresh backend instance over the same log file after a simulated restart still reports a previously consumed nonce; a byte-identical resubmission is idempotent; a changed-byte reuse of a consumed nonce is refused (`"replayed"`).
- Account-authorized revocation is implemented, bound to the exact target Device binding (deviceId AND device public key), terminal, idempotent on duplicate, and denied for the wrong account — proven directly, including that a revoked device cannot be re-registered under the same `deviceId` even with a fresh, valid, correctly-signed challenge.
- `UnavailableFedosDeviceRegistrationAuthority` (Alpha 2921–3000) is untouched and re-confirmed, by direct test in this Arc, to still never return `"verified"`.
- A Phase J factory/adapter (`fedos_device_binding_boundary_factory.ts`) exists as the one future Desktop Runtime integration point — proven end-to-end (mint a challenge, sign both proofs, register) — while remaining completely unwired from `fedos_desktop_runtime.ts` in this Arc.
- A genuine pre-existing bug was found and fixed: `isWellFormedFedosDeviceBindingChallengeV1`'s field-count guard checked for 7 keys against an 8-field interface, rejecting every well-formed challenge unconditionally. Caught by this Arc's own first real-crypto test, fixed in the same file, in the same commit.

## What this Arc explicitly does NOT claim

- **No claim the Device is malware-free, physically controlled by the intended human, or online.** The boundary proves a signature was produced by a key; it says nothing about the environment holding that key.
- **No synchronization occurred, no remote deletion occurred.** This Arc implements proof and registration authority only — explicitly NOT device-to-device synchronization transport (named out of scope by this Arc's own instructions).
- **No claim the Master Seed is absent from the Device.** This Arc does not implement or verify any device-attestation or secure-enclave boundary.
- **No forward secrecy claim, no Sender-Key distribution security claim.** Both are out of scope; neither Sender-Key device distribution nor MLS nor Onion/Tor is implemented anywhere in this Arc.
- **No distributed exactly-once replay guarantee.** The replay guard is a single-writer, in-process guard (Node's own single-threaded execution model) — stated honestly in-file and here, not merely implied.
- **No Desktop Runtime activation.** The factory/adapter exists; it is not called from `fedos_desktop_runtime.ts`. A device registered through this Arc's own orchestrator in a test or a future caller is real and durable, but no production Runtime code path exercises it yet.
- **No upgrade path for a pre-existing `"unavailable"` binding** created by the legacy Alpha 2921–3000 adapter. This Arc's orchestrator maps that case to `"unsupported"` rather than silently failing or fabricating an upgrade — a genuinely-owned device re-registers under a new `deviceId`.
- No new dependency, no Rust/WASM change, no Desktop Shell change, no Archive/Search/Sender-Key/Group Runtime change.

## Security Statement (Phase L)

**What this boundary proves:**
- The account (identified by its real, cryptographically-verified Nostr public key) authorized the exact binding challenge in hand — not a different device id, device key, action, expiry, or nonce.
- The Device proved possession of the private key corresponding to the public key named in that same challenge.
- The Device Registry accepted that binding only after both of the above were independently re-verified in this same call.
- Replay and expiry rules were applied: a consumed nonce cannot authorize a second binding; an expired challenge is denied; a byte-identical resubmission is idempotent rather than silently reprocessed.

**What this boundary does NOT prove:**
- That the Device is malware-free.
- That the Device is physically controlled by the intended human.
- That the Device is online, or that any synchronization has occurred.
- That any remote deletion has occurred (revocation denies future authority; it does not erase history or reach into the revoked device).
- That the Master Seed is absent from the Device.
- Forward secrecy of any kind.
- Sender-Key distribution security.

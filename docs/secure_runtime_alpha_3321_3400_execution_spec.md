# Secure Runtime Alpha 3321–3400: Device Registration Runtime Activation and Local Device Sync Foundation — Execution Spec

Architecture frozen. This Arc redesigns nothing: no change to `src/sync/`, `src/device/fedos_device_binding.ts`, `src/device/persistence/` (the Alpha 2921–3000 Device Registry), `src/device/binding_challenge/` (the Alpha 3161–3240 Account-to-Device Signature Verification Boundary), Conversation Runtime, Archive, Search, Sender-Key, or Desktop Shell; no new Rust/WASM primitive; no new dependency. It activates the Registration Authority Alpha 3161–3240 built but explicitly did not wire anywhere, and adds the LOCAL (no network/cloud/relay) data model a future device-to-device transfer would need.

Base revision: worktree `C:\wt\device-sync-foundation`, branch `arc/device-sync-foundation`, based on `master` tip `0f8ac0b` (Secure Runtime Alpha 3161–3240, "Account-to-Device Signature Verification Boundary").

## Phase A — Source reconciliation

1. **The Registration Authority already exists, unwired**: `createFedosDeviceBindingBoundary()` (`src/device/binding_challenge/fedos_device_binding_boundary_factory.ts`) builds a `FedosDeviceBindingRegistrationAuthority` (`registerDevice`/`revokeDevice`/`getBinding`) plus a `mintChallenge()` minter, over caller-supplied `FedosDeviceRegistryPersistence` + `FedosDeviceBindingChallengeReplayPersistence`. Its own file header names the exact integration step left undone: "the ONE narrow construction point a future Desktop Runtime integration step would call... This Arc does NOT wire this factory into `fedos_desktop_runtime.ts`."
2. **Local Device Inventory does not exist as a named capability**: `FedosDeviceRegistryPersistence.listBindings()`/`listBindingsForAccount(authority, publicIdentifier)` (`src/device/persistence/fedos_device_registry_persistence.ts`) already expose every binding, but nothing outside the legacy, Desktop-Runtime-owned `FedosDeviceTrustRuntime` reads them as an "inventory" concept, and that Runtime is wired to the OTHER (unverified/legacy) registration path (`UnavailableFedosDeviceRegistrationAuthority`), not the Alpha 3161–3240 verified boundary.
3. **No Sync Session or Sync Package concept exists anywhere**: `src/sync/` (Alpha 2421–2500/2921–3000) is a separate, unmodified device-label/journal/cursor/queue fabric with its own opaque `FedosSyncDeviceBinding` type, explicitly documented as never carrying plaintext/ciphertext content. No file in this repository builds, encrypts, or reads a "session" or "package" bundling a Device Registry inventory.
4. **No symmetric-cipher npm dependency exists**: `package.json` production dependencies are exactly `@noble/curves` and `@noble/hashes` — no AEAD library. Real AEAD lives entirely behind the WASM Runtime Service (`src/runtime/fedos_runtime_encrypt.ts`/`fedos_runtime_decrypt.ts`/`fedos_runtime_export_ciphertext.ts`/`fedos_runtime_import_ciphertext.ts`), gated by a closed `AeadAadDomain` enum (`"RootKey"|"Identity"|"Storage"|"Conversation"|"TestOnly"`, `src/runtime/fedos_wasm_loader.ts`) mapped 1:1 to `packages/fedos-core-rust/src/lib.rs`'s own discriminants. Adding a `"Sync"` domain would require a Rust change — out of scope.
5. **Existing reuse precedent for exactly this constraint**: `src/conversation/archive/fedos_conversation_archive_encryption.ts` (Alpha 1541–1610) already reuses the `"Conversation"` `AeadAadDomain` for a non-message payload (a whole Conversation Archive) rather than adding a new domain, and already reuses `FedosMasterSeedAuthority.resolveConversationKey(accountIndex, counterpartyPublicKeyHex)` for a purpose beyond pairwise messaging. This Arc's Encrypted Sync Package follows the identical reuse discipline (Phase E).
6. **Account public-key retrieval** (unchanged, Alpha 684/3161–3240): `FedosNostrSigningAuthority.publicIdentityForAccount(accountIndex)` — derives the account's own `publicKeyHex` without signing anything.
7. **Expected files to change**: three new directories — `src/device/runtime/` (the Device Sync Runtime facade), `src/device/sync_session/` (Sync Session type + prepare/validate), `src/device/sync_package/` (Encrypted Sync Package type + header + manifest + Builder/Reader) — plus this Arc's docs, tests, and a README status blurb. `src/device/binding_challenge/`, `src/device/persistence/`, `src/device/fedos_device_binding.ts`, `src/sync/`, `src/conversation/`, `src/nostr/`, and Desktop Shell/`fedos_desktop_runtime.ts` are byte-for-byte unmodified.
8. **Baseline failures**: `npm run typecheck` clean except the one pre-existing, unrelated `test/secure_runtime_alpha_477_scheduler_lifecycle_model.test.ts:121` error (present identically in the primary, non-worktree checkout — already named by every recent completion declaration). `npm test` on a fresh worktree shows the two already-documented environmental artifact classes — `?raw`-import Cargo.toml/lib.rs empty-content failures ([[project_worktree_raw_import_artifact]]) and `test/reviews/**` git-status snapshot assertions reacting to this Arc's own new untracked files before commit — neither caused by this Arc's own code.

## Phase B — Device Sync Runtime (Registration / Activation / Revocation / Inventory / Status)

`src/device/runtime/fedos_device_sync_runtime.ts` — `FedosDeviceSyncRuntime`, constructed via the ONE factory `createFedosDeviceSyncRuntime(deps: FedosDeviceBindingBoundaryDeps)` (the exact same dependency shape `createFedosDeviceBindingBoundary()` already takes — no new persistence port, no new backend).

- **Runtime Device Registration**: `mintChallenge(action, deviceId, devicePublicKeyHex)` — thin delegation to `boundary.mintChallenge()`.
- **Runtime Device Activation**: `registerDevice(accountAuthorization, deviceProof, now)` — thin delegation to `boundary.registrationAuthority.registerDevice()`. Registration and Activation are ONE atomic call in this verified path: `AlreadyVerifiedFedosDeviceRegistrationAuthority` (internal to `FedosDeviceBindingRegistrationAuthority`, Alpha 3161–3240) always resolves `capability: "verified"` once both signatures check out, so this call already reaches `"registered-trusted"` — there is no separate `"pending"` state a caller must flip in this path, unlike the legacy `FedosDeviceTrustRuntime`'s own separate `confirmTrust()` step, which this Runtime does not use and does not need.
- **Runtime Device Revocation**: `revokeDevice(accountAuthorization, now)` — thin delegation to the same boundary; terminal, account-authorization-only.
- **Local Device Inventory**: `getDevice(deviceId)`, `listDevices(accountRef)`, `listActiveDevices(accountRef)` — read DIRECTLY from the injected `FedosDeviceRegistryPersistence` (the SAME instance the boundary was built over), via its own EXISTING `listBindings()`/`listBindingsForAccount()`. No second, parallel inventory of any kind is introduced.
- **Device Status Queries**: `deviceStatus(deviceId): { deviceId, found, trustState, active }` — `found: false`/`trustState: "unknown"` (never a thrown error) for a device with no Registry record at all.

Decision considered and rejected: extending `FedosDeviceTrustRuntime` (`src/desktop/runtime/fedos_device_trust_runtime.ts`) in place. Rejected — that class is Desktop-Runtime-owned, wired to the LEGACY (`UnavailableFedosDeviceRegistrationAuthority`) path, and already bridges into `src/sync/`'s own fabric for a different reason (device-label sync-fabric membership, not Device Registry verification). Building a new, parallel facade over the SAME persistence port keeps both Runtimes fully independent and avoids any risk of retrofitting verified-path semantics onto a class whose own contract (and existing tests) assume the legacy path.

## Phase C — Sync Session Preparation and Validation

`src/device/sync_session/fedos_device_sync_session.ts` — `FedosDeviceSyncSessionV1 { schemaVersion, accountAuthority, accountPublicIdentifier, targetDeviceId, preparedAt, expiresAt, nonce, devices: [{deviceId, devicePublicKeyRef, trustState}] }`. A Sync Session is a LOCAL, at-rest snapshot of one account's currently-`"trusted"` Device inventory, addressed to one target Device that is itself currently trusted — the exact LOCAL data a future "Encrypted Device-to-Device Local Transfer" Arc would hand to its own transport. No network/relay/cloud behavior of any kind is implemented here.

- `prepareFedosDeviceSyncSession(deps)` — refuses to prepare a session for a `targetDeviceId` that is not currently `"trusted"` for the given `accountRef` in the LIVE Registry (`"target-not-found"`/`"target-not-trusted"`) — the "unauthorized Device" refusal named in this Arc's own test matrix. `devices` is every currently-`"trusted"` binding for the account, sorted by `deviceId` for a deterministic snapshot.
- `validateFedosDeviceSyncSession(deps)` — re-checks a session against the LIVE Registry at validation time, never trusting the session's own frozen `devices` list at face value: `"malformed"` (structural), `"expired"` (`now > expiresAt`), `"target-not-trusted"` (the target Device itself is no longer live-trusted, independent of expiry), `"stale-device-list"` (a Device the session lists as trusted is no longer live-trusted — revoked or removed since preparation).
- `fedos_device_sync_session_codec.ts` — deterministic canonical byte serialization (sorted `devices`, fixed field order), fail-closed to `null` on any malformed/off-schema input. This is exactly the byte sequence the Encrypted Sync Package Builder/Reader seals and opens (Phase E).

## Phase D — Encrypted Sync Package: Header and Manifest

`src/device/sync_package/fedos_device_sync_package_header.ts` reuses `fedos_conversation_archive_header.ts`'s own "prefix-then-encrypt" technique verbatim (length-prefixed canonical bytes of `{accountAuthority, accountPublicIdentifier, targetDeviceId, preparedAt}`, prepended to the session bytes before sealing, stripped and byte-compared after opening) — binding the Package's identity, since the real `encrypt()`/`decrypt()` Runtime Service accepts only the closed `AeadAadDomain` enum with no free-form associated-data parameter.

`src/device/sync_package/fedos_device_sync_package_manifest.ts` — `FedosDeviceSyncPackageManifestV1 { schemaVersion, accountAuthority, accountPublicIdentifier, targetDeviceId, preparedAt, expiresAt, deviceCount, contentHash }` — travels ALONGSIDE the ciphertext, in the clear, never itself AEAD-protected; `contentHash` is `sha256` of the canonical session bytes, binding the Manifest to the session's CONTENT (distinct from the Header's identity binding), mirroring the Archive's own two-layer Header/Integrity split exactly.

## Phase E — Encrypted Sync Package Builder / Reader

`src/device/sync_package/fedos_device_sync_package_encryption.ts` — `FedosWasmDeviceSyncPackageEncryptionAuthority.build()`/`.read()`.

**Key resolution — the one adaptation this Arc makes, stated explicitly**: a Sync Package is LOCAL and single-account, addressed to one of the account's OWN Devices — there is no second party to ECDH against the way `resolveConversationKey(accountIndex, counterpartyPublicKeyHex)` was designed for (pairwise conversation messaging). This Arc resolves the SAME function against the account's OWN public key (`selfAccountPublicKeyHex`, caller-resolved via `FedosNostrSigningAuthority.publicIdentityForAccount()`, mirroring the Archive's own "already resolved by the caller" convention for `counterpartyPublicKeyHex`). `ECDH(a, a·G)` is a legitimate encrypt-to-self construction — only the holder of the account's own Master Seed (secret `a`) can ever reproduce this key. This restates the Archive's own "you can decrypt your Export iff you can already decrypt that conversation" justification as "you can open your own Sync Package iff you hold this account's own Master Seed." No new key-derivation Rust export is added; no new `AeadAadDomain` variant is added (`"Conversation"` is reused, for the identical reason the Archive already reuses it — see Phase A.5).

Decisions considered and rejected: (a) add a new `"Sync"` `AeadAadDomain` — rejected, requires a Rust/lib.rs change, out of scope (Architecture Frozen, no Rust change named anywhere in this Arc's instructions); (b) add `@noble/ciphers` and encrypt directly in TypeScript — rejected, violates "no new dependencies" and duplicates the existing, real, production AEAD path for no benefit; (c) leave the Package unencrypted (signed/MAC'd plaintext only) — rejected, the task names an "Encrypted Sync Package Builder/Reader" explicitly, and the self-ECDH construction above achieves real confidentiality without any of the above trade-offs.

Failure vocabulary mirrors `FedosConversationArchiveExportResult`/`ImportResult` (`"key-unavailable"|"invalid-input"|"failed"`, `"manifest-mismatch"`), plus this file's own two additions: `"malformed"` (before any decrypt is attempted — a structurally-invalid `FedosDeviceSyncPackageV1`) and `"expired"` (the Manifest's own `expiresAt`, checked independently of the session's own expiry so a caller reading a Package alone still gets an honest answer before ever decrypting).

## Security Statement

- No raw Device secret key, account secret key, or AEAD key byte is ever returned by any new file in this Arc.
- Runtime Device Registration/Activation/Revocation add NO new verification logic — every signature/replay/expiry check remains exactly Alpha 3161–3240's own, unmodified, re-used through its own public `FedosDeviceBindingRegistrationAuthority`/`createFedosDeviceBindingBoundary()` surface.
- Local Device Inventory and Device Status Queries are read-only projections of the EXISTING Device Registry; they cannot mutate trust state and introduce no new persistence.
- Sync Session Preparation independently re-checks the target Device's live trust state before ever including it; Sync Session Validation independently re-checks EVERY listed Device's live trust state, never trusting a previously-prepared snapshot.
- The Encrypted Sync Package's self-ECDH key resolution reuses an existing, reviewed WASM/Rust code path unmodified; this Arc adds no new cryptographic primitive and no new `AeadAadDomain` Rust discriminant.
- This is a single-writer, in-process guard against replay (inherited from Alpha 3161–3240) — no distributed exactly-once claim is made, exactly as that Arc already stated.
- No network, relay, or cloud transport of any kind is implemented — Sync Sessions and Packages are LOCAL, in-process/on-disk data only.

# Secure Runtime Alpha 3721–3800: Background Device Sync Scheduling and Conflict Resolution — Completion Declaration

## What this Arc proves

- A restart-safe, explicitly-activated Scheduler boundary (`FedosDeviceSyncScheduler`) turns the existing manually-invoked Relay Device Sync flow into a controlled background process: disabled by default, no hidden timer, `startSync()`/`stopSync()`/`syncStatus()`/`tickSync()`/`triggerSyncNow()` — proven directly by 5 activation tests, 3 single-flight tests (including a throwing `attemptFn` never producing an unhandled rejection and still releasing the guard), and 3 restart/isolation tests.
- Target Planning (`planFedosDeviceSyncTargets`) proves it queries the LIVE Device Registry, excludes the source Device and any revoked target, respects a pending-range cap, and never infers online status — proven with a real trusted target, real multiple trusted targets, a real revoked target excluded entirely, and a target with genuinely nothing pending.
- Durable Schedule state survives a real, simulated crash: a Schedule left `"in-progress"` by an un-awaited, never-settling `attemptFn` is recovered to `"pending"` and completed on the very next tick by a FRESH `FedosDeviceSyncScheduler` instance reading the SAME append-only NDJSON log — proven directly, not asserted.
- Retry classification is closed and abandonment is explicit: a transient outcome (`"relay-timeout"`) is scheduled for retry-later with `nextEligibleAt` advanced past `now`; a permanent rejection (`"revoked-target"`) is terminal (`"failed"`), never retried; repeated transient failures beyond an explicit, injected `maxAttempts` become `"operator-required"`, never silently infinite — proven directly across two sequential ticks with an advancing clock. The Scheduler's own constructor REJECTS a missing or malformed `abandonmentPolicy` — no arbitrary default retry count exists anywhere in this Arc.
- The richer, 11-value Conflict Vocabulary correctly distinguishes an identical duplicate from a genuinely concurrent update from invalid/untrusted data — proven by 12 direct classification tests covering every named kind, including the priority ordering between them (e.g. a disallowed record type wins over a trust check, which wins over a sequence-gap check).
- Domain-specific resolution planning is proven for all four named domains (insert-once/immutable, append-only-safe, tombstone-vs-upsert, locally-re-derivable projection) plus the safe/unsafe generic cases (identical-duplicate, missing-dependency, cursor-divergence, unknown-record-type, revoked-device-contribution) — each mapped to one of 7 closed decisions with a stated reason, verified against the literal `PLAN_TABLE`.
- Import Coordination proves that `FedosSyncState.applyPendingChanges()` (Alpha 2421–2500, byte-for-byte unmodified) is called exactly once per import and every result — INCLUDING an otherwise-clean base `"applied"` outcome — is reclassified through the richer vocabulary: a contribution from an origin Device revoked AFTER it contributed a Journal entry is caught and durably recorded as `"revoked-device-contribution"` even though the base classifier (which has no Registry reference) reported nothing wrong; an unknown, non-allowlisted record type is likewise caught even on an `"applied"` base outcome. Both are real integration-level proofs, not merely unit-level classification proofs.
- Operator-required conflicts are durably queryable and only objectively-safe resolution actions are ever accepted: an unsafe action for a given `conflictKind` (e.g. `"accept-identical"` against an `"immutable-record-conflict"`) is explicitly REJECTED (`"unsafe-action"`) — proven directly, alongside a genuine `"acknowledge"` resolution succeeding for the same conflict. There is no "force overwrite canonical state" command anywhere in this Arc's own code.
- Restart-safety for BOTH new durable stores is proven independently: a fresh `AppendOnlyFedosDeviceSyncSchedulePersistence`/`AppendOnlyFedosDeviceSyncConflictPersistence` instance over the SAME log file recovers full, correct state after a simulated process restart.
- Account and Runtime isolation are proven directly: two Schedulers over completely separate accounts, and two Schedulers over the SAME account/state but separate schedule persistence, never see or interfere with each other's schedules.

## What this Arc explicitly does NOT claim

- **No distributed consensus, no distributed exactly-once guarantee, no strong eventual consistency claim.** This Arc's own convergence property is narrower and explicitly stated: a well-formed, non-conflicting change reaches every currently-trusted target Device's local Cursor exactly once (durable dedup, Alpha 3641–3720, unmodified); a genuinely conflicting/invalid/untrusted contribution is durably surfaced for operator review, never silently applied and never silently dropped.
- **No last-write-wins by default, anywhere.** Every conflict this Arc's own vocabulary names is resolved by NAMED domain semantics (Phase I) or explicitly deferred to an operator — there is no generic timestamp-wins resolver in this Arc's own code.
- **No wall-clock time used as the sole conflict authority.** Conflict classification is sequence/Cursor-based (`incomingSequence`/`localCursorSequence`) and Device-trust-based, never a bare timestamp comparison; `nextEligibleAt`/`firstObservedAt`/`lastObservedAt` are scheduling/observation metadata, never used to decide WHICH of two conflicting records wins.
- **No silent overwrite of a conflicting canonical record, ever.** Every plan that is not `"apply"`/`"skip-identical"` is durably recorded as an unresolved Conflict fact BEFORE this Arc's own coordination logic returns — proven directly by the conflict-persistence tests.
- **The Sync Journal's own Cursor-advance semantics are NOT changed.** `FedosSyncState.applyPendingChanges()` still advances a target Device's Cursor past every pending entry unconditionally, by its own accepted, Alpha 2421–2500 design. This Arc does not, and explicitly does not attempt to, make the Cursor itself block on a conflicting record — "the unresolved blocking record remains visible" is satisfied by a SEPARATE, independent Conflict persistence/query layer instead (Phase K/L's own documented atomicity model), not by altering Cursor behavior.
- **No end-to-end proof against the real Alpha 3641–3720 Outbound Coordinator or a real in-process Relay fixture.** The Scheduler's own `FedosDeviceSyncAttemptFn` boundary is exercised with hand-written attempt functions delivering every outcome code this Arc's retry policy needs; Relay Sync itself is already proven end to end in Alpha 3641–3720's own 50 tests, and re-proving it here would duplicate that Arc's own coverage rather than prove anything new about the Scheduler.
- **A genuine base `"duplicate"` outcome through the Import Coordinator's integration surface is not proven** — `FedosSyncPendingChangeQueue.enqueue()` (unmodified) makes it structurally unreachable through the public API (see the Execution Spec's own Phase O for the full explanation). The underlying classification/planning logic IS proven directly at the unit level.
- No cloud sync, no central synchronization authority, no push notifications, no background OS service, no Onion/Tor, no MLS, no Desktop Shell/UI change, no new dependency, no Rust/WASM change.

## Security guard scan

`grep` (case-insensitive) across every new file under `src/device/sync_scheduler/` for `masterseed`, `private_?key`, `passphrase`, `mnemonic`, `nsec`, `bearer` — zero matches. `grep` for `Math.random` — zero matches (the only nonce generation in this Arc reuses the EXISTING, unmodified `FedosSecureRandomDeviceBindingChallengeNonceGenerator`). No new file constructs a raw private key, reads the Master Seed, or places any such value in a Sync record or Schedule/Conflict persistence field — every persisted field is a non-secret fact (device id, sequence number, timestamp, coarse outcome string, closed-vocabulary enum value).

**One genuine bug found and fixed during test-writing**, in the same class this repo's own history already records finding repeatedly (Alpha 3161–3240, 3481–3560, 3641–3720 completion declarations): the Schedule event codec's four field-count guards were each off by exactly one (checked 7/5/6/4 against 8/6/7/5-field interfaces), rejecting every genuinely well-formed event — caught and fixed before any test was allowed to pass. A second, non-off-by-one bug was caught by self-review before running any test: the Conflict Authority's `PLAN_TABLE` initially had no entry at all for `"immutable-record-conflict"` — added (`"record-conflict"`) before the first test run. A third, more substantive bug was caught only by writing the Import Coordinator's own integration tests: the original implementation only reclassified a base `"duplicate"`/`"conflict"` outcome through the richer vocabulary, silently passing through every base `"applied"`/`"archived-skip"` outcome untouched — meaning a Device revoked AFTER contributing a Journal entry, or a disallowed record type, would sail through unflagged whenever the entry happened to be the FIRST one for its conversation (the common case, since `FedosSyncState`'s own base classifier only ever reports a problem when comparing against a PRIOR applied entry). Fixed by reclassifying every result unconditionally, with a progressively-tracked local Cursor (rather than one stale batch-start snapshot) to avoid a corresponding false-positive `"missing-dependency"` flood across multi-entry batches.

## Security Statement

**What this Arc's Scheduler and Conflict Resolution prove:** that background Relay Device Sync can run on a fixed cadence without ever running two attempts concurrently, without ever attempting a Device that is not currently, live-trusted, without ever exceeding an explicit resource limit, and without ever silently losing track of an attempt interrupted by a crash; that a well-formed, non-conflicting contribution from a currently-trusted Device converges to every other trusted Device's local state; that a conflicting, invalid, or untrusted contribution is durably classified by real domain semantics and surfaced for the smallest set of objectively-safe operator actions — never silently applied, never silently dropped, and never resolved by an arbitrary or forced overwrite.

**What this Arc's Scheduler and Conflict Resolution do NOT prove:** any distributed-systems consistency guarantee stronger than "durable local dedup plus durable, queryable conflict surfacing"; that the Sync Journal's own Cursor-advance-past-everything design (Alpha 2421–2500, unmodified) is itself changed in any way — a conflicting record's Cursor position still advances, and this Arc's own honest atomicity model relies entirely on the SEPARATE Conflict persistence layer for visibility, not on Cursor semantics; any end-to-end proof against the real Alpha 3641–3720 Relay Sync Outbound Coordinator (proven separately, in that Arc's own test suite); any capability this Arc's own Absolute Prohibitions explicitly named as out of scope (cloud account server, central synchronization authority, push notifications, background OS service).

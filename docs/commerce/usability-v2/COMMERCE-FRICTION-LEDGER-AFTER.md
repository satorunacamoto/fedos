# FedOS Commerce — Friction Ledger, AFTER (Coordinator Synthesis)

Consolidated from the fresh, uncoached Buyer ("Alice") and Seller ("Bob") tabletop passes against `arc/fedos-commerce-real-two-party-ux-closure` post-merge. Same severity discipline as v1: **P0** = user cannot safely complete the transaction, or is misled about payment/delivery/product-state truth, or the UI is security-critically misleading. **P1** = high abandonment/confusion risk on the core flow even if nothing is technically unsafe. **P2** = meaningful friction/discoverability problem. **P3** = polish.

| # | Actor | Finding | Severity | Status vs. v1 |
|---|---|---|---|---|
| 1 | Both | No path to discover a real, independently-published seller's listing from the *ordinary*, unconfigured buyer flow — no default Relay, Commerce Nostr Publication defaults to Local-Only and does not persist across restart. | **P0** | **Root cause changed, symptom unchanged.** v1: structurally impossible (no networked discovery existed). AFTER: the mechanism is real and independently proven (two-process E2E), but default configuration still blocks an ordinary first-time user from reaching it. |
| 2 | Buyer | Seller shows as "Unknown merchant" then a raw pubkey throughout the *entire* buyer journey, even for a correctly-created real-profile listing — no seller/store display-name field exists anywhere in product creation. | **P1** | **New, real gap** the v1 baseline could not have found (it never had a real, attributed cross-identity listing to test against). Directly undermines "decide whether I trust it." |
| 3 | Seller | No field anywhere to attach the actual protected/digital deliverable to a listing; a buyer sees an honest "no content" message even after a fully completed, confirmed purchase. | **P1** | **Confirms and sharpens v1's own finding** ("a complete, tested, signed protected-media entitlement system exists with zero production callers"). AFTER: the entitlement *authorization* machinery is now real and correctly wired (Agent D) — but there is still no real path for a seller to upload content in the first place, so digital delivery remains incomplete end-to-end. |
| 4 | Buyer | Signed receipt did not survive a real (dev-mode) app restart — reopens as if "Issue" was never clicked, no warning, silent re-issuance produces a new but different proof. | **P1 — DISCREPANCY, unresolved.** | This directly contradicts the coordinator's own live-verified `commerce_e2e_packaged_binary_restart_real_electron.test.ts` (byte-identical receipt digest across a real installed-binary restart, re-verified twice this arc). | 5 | Seller | "Attach Image" is live in the UI but fails 100% reproducibly with an unhelpful `"image storage failed: failed"` message — no cause given, no recovery path. | **P1** | **New finding.** Agent D wired a real image-attach IPC path; this specific UI/IPC integration has a real, reproducible defect not caught by that agent's own automated tests. |
| 6 | Seller | Switching seller identity on My Store can silently blank "My Products"/"Incoming Orders" (reads as data loss) until navigating away and back — single-process, no relay involved. | **P1** | **New finding**, a real render-state bug distinct from the underlying (correct) data. |

| 10 | Buyer | Search tab is messages-only, not product search — a first instinct for "find a specific thing" doesn't work. | **P3** | Not previously tested/found in v1 (v1's discovery gap made this moot). |

**Totals:** UX-P0: **1** (root cause changed, symptom persists) | UX-P1: **5** (1 unresolved discrepancy requiring follow-up, not a confirmed regression) | UX-P2: **3** | UX-P3: **1**.

**Closed since v1 (confirmed fixed, not merely claimed):** the "Unknown merchant" mis-attribution *at creation time* (row #2 in v1 — a real domain-authority fix, verified independently by both tabletop agents creating correctly-attributed listings without incident); the Publish double-click archiving bug (both agents confirmed a single click, no accidental archive); "Request Payment" buyer-facing naming and its underlying non-idempotency defect; receipt QR now actually renders an image; reputation now visible on the seller's own dashboard; zero `try/catch` around Commerce IPC (both agents' real failures produced an actual error state, not a silent hang or stack trace) — though 2 of those newly-surfaced error states are themselves new P1 findings (rows 5, 6), which is the honest outcome of testing a real, exercised error path for the first time rather than the same defect recurring.

## Commerce Durability + Protected-Media Entitlement + Packaged-E2E FINAL Closure arc update

Closes **Gap #16** (Commerce domain state persistence — durable, restart-proven) and **Gap #17** (protected media purchase-grant binding — now exists as a real, signed, tested `MediaAccessGrant`, though not yet wired into a live IPC handler since none exists to wire it into). **Gap #18** (packaged-binary E2E) is **narrowed, not closed**: a real packaging bug (node_modules never bundled at all) is found and fixed, and two harness bugs are fixed along the way, but the full happy path still does not complete against the packaged binary in this environment — see `docs/commerce/FEDOS-COMMERCE-END-TO-END.md`'s own "Commerce Durability" section for the precise, narrowed root-cause account.

**New gap this pass, not previously tracked:** `buyerPubkey === sellerPubkey` (self-dealing) was never forbidden by the Order domain layer itself — `createOrder()` validated every other field but never compared the acting customer's own pubkey against the seller's. Classified **P1** on the same "core journey" basis as the other gaps below, though it is a correctness/integrity gap rather than a missing-capability one. **CLOSED this pass** — `createOrder()` now rejects with a new `self_dealing` code, unconditionally, with no bypass path found anywhere in the commerce tree.

## Commerce FINAL Closure Mega-Arc update (current, additive)

Verified at CandidateHead `7e0d9f0a9611792dea6cfcaf077bb37528575bf1` / `b447dfcc899b6c713606f36f02351bc566636e3e`. This arc closes **Gap #9's remaining media follow-up** (protected media crypto is now the real default composition, fails closed) and adds real coverage for two capabilities this table never tracked as gaps because they postdate it: **Reputation/Persona attestation** (now real and wired — see `docs/commerce/REPUTATION-PERSONA-EPOCH-DESIGN.md`) and **Nostr Commerce publication** (now real and wired, default-off via `NetworkProfile`).

A FedOS Desktop Beta restart silently loses every product, order, delivery, payment, and reputation record created since the last launch. Classified **P1** (core journey incomplete for a real pilot user, but no authority/security guarantee is weakened — every guarantee this table and the cross-capability spot-check assert holds true within a single process lifetime).

## Commerce E2E Completion arc update (current, additive)

The Commerce E2E Completion arc closed **Gap #3** (Order), **Gap #6** (merchant UI: create/edit/publish/incoming-orders/accept/reject/fulfill), **Gap #7** (delivery/fulfillment — a real `DeliveryRecord` state machine, not `DigitalAsset`), **Gap #8** (Commerce↔Trust wiring — a real signed `TradeReceiptProof` issued on order completion), **Gap #12** (customer order/receipt UI), and **Gap #13** (QR now carries a real signed trade receipt). **Gap #4 (real payment rail) remains open BY DESIGN, not by omission** — this arc's own brief explicitly forbids wiring a real payment rail or moving real money; payment is a `DeterministicLocalPaymentProvider`, constructed only with `{ acknowledgeTestOnly: true }` and refusing `runtimeProfile: "production"` outright, callable only from this process's own composition root (no external network callback surface — it is not the same code path Gap #5 describes). **Gap #5 (`PlaceholderPaymentProvider.ingestCallback()` unauthenticated)** is unchanged — that specific dormant provider is untouched by this arc, and is not the one used by the new local simulator flow.

**Gap #10 (no inventory/stock field)** remains open and now has its stated dependency satisfied (Order exists) — a reasonable next-arc candidate.

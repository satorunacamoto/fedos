# Secure Runtime Alpha 5321-5400 — Certificate Custody Policy and Future Signing Integration Seam

## Certificate custody policy (Phase M)

FedOS Desktop Beta 0.1 ships **unsigned**. This document records the policy a future Arc should follow once code signing becomes a real requirement — it creates no certificate, requests no password, and stores no secret.

### Options considered

| Option | Control | Key location | Suitability |
| --- | --- | --- | --- |
| Local `.pfx`/`.p12` file on a developer machine | Single developer | Local disk | **Rejected for production.** A file-based private key on a developer workstation is a single point of compromise with no audit trail; this is the exact anti-pattern this Arc's own Absolute Prohibitions guard against (no `.pfx` is ever committed or generated by this codebase). |
| OS certificate store (Windows "Personal"/"My") | Single developer/build machine | OS-protected store | Marginally better than a bare file (non-exportable key option exists) but still ties signing capability to one machine's compromise state, and to whichever individual account holds it. |
| Hardware token / HSM (e.g. a USB EV code-signing token) | Whoever holds the physical token | Hardware, never exportable | **Preferred production direction.** EV/OV code-signing CAs increasingly *require* hardware-backed keys. Signing requires physical possession, which is a real, auditable control; the private key material never leaves the device. |
| Managed cloud signing service (e.g. a CA-operated signing API, or a self-hosted signing server behind an internal API) | Organization-level access control (IAM roles, audit log) | Provider-managed HSM | **Preferred production direction, especially for CI-driven releases.** Signing becomes an authenticated API call with its own audit trail; no key material ever touches the build machine. This is the recommended target once releases are cut from an automated pipeline rather than a developer's own machine. |
| CI secret (a `.pfx` + password stored as CI secrets, decrypted at build time) | CI platform's own secret-store ACLs | Ephemeral, in CI worker memory only | **Permitted temporary fallback only**, and only if the CI platform's secret store has hardware-backed encryption at rest and the secret is scoped to the minimum number of pipelines/people. This trades "no key ever touches a developer machine" for "the CI platform itself becomes the trust boundary" — acceptable as a bridge, not as the permanent answer. |

**Recommendation**: a hardware token for the current (small-team, non-CI) release process, migrating to a managed cloud signing service once releases are cut from CI. **A `.pfx` file recommended for storage anywhere in this repository, on a shared drive, or in an unencrypted state is never acceptable** — this document explicitly does not recommend it under any circumstance.

### Custody controls, whichever option is chosen

- **Control**: exactly one named individual (or one CI service identity) may invoke a signing operation at a time; every signing event is logged (who, when, which artifact hash was signed).
- **Key location**: never inside this repository, never inside `release/` or `release-staging/`, never inside a Git commit or tag.
- **Password handling**: a certificate password (if the option in use has one) is never typed into a shell history, never stored in a plaintext file, never logged, and never passed as a plain CLI argument (environment variable injection or a secret-manager reference only).
- **Backup**: the private key (or the hardware token itself) is backed up according to the issuing CA's own escrow policy, or a second hardware token is provisioned — never a plaintext export.
- **Rotation**: a certificate is rotated before its own expiry, with enough lead time to re-sign a pending release if needed; rotation is itself logged.
- **Revocation**: if a signing key is suspected compromised, the certificate is revoked with the issuing CA immediately, and a `revoked`-status advisory (`scripts/lib/revocation_status.mjs`) is published for every release signed with it, per the existing tag policy's own `"keep-tag-publish-advisory"` rule (`scripts/lib/tag_format.mjs`).
- **Build-machine compromise**: because the private key never resides on the build machine (hardware token or managed service), a compromised build machine cannot exfiltrate the signing key — at most it could request an unauthorized signing operation, which the custody control above (one named identity, logged) is designed to catch.
- **Developer access**: no developer other than the person/service performing a specific release needs signing access; access is granted per-release, not standing.
- **Timestamping**: every real signing operation MUST use an RFC 3161 timestamp server (`assessFedosSigningReadiness`'s own `timestamp-service-unconfigured` outcome exists specifically to block signing readiness until this is configured) — an un-timestamped signature becomes invalid the moment the certificate expires, silently breaking every previously-signed release.
- **Incident response**: a suspected key compromise triggers, in order: (1) revoke the certificate with the CA, (2) publish a `revoked` advisory for every affected release version, (3) rotate to a new certificate under the same custody policy, (4) re-sign and re-publish affected releases under new version numbers (never by mutating an existing tag, per `FEDOS_BETA_TAG_POLICY.allowRetagging === false`).

## Future signing integration seam (Phase N)

The intended, additive seam for a future signing Arc — no code changes are made to implement this seam now, only the boundary is documented and proven not to silently accept stale artifacts:

```
verified unsigned artifacts (release/, this Arc's own build_release.mjs output)
        │
        ▼
signing readiness check (assessFedosSigningReadiness — already implemented, this Arc)
        │  (only proceeds past this point once outcome === "signing-ready")
        ▼
external/manual signing step (signtool sign, or a managed signing service call —
        NOT implemented by this Arc; explicitly prohibited by this Arc's own scope)
        │
        ▼
signature verification (a future Arc's own step: signtool verify / Authenticode chain check)
        │
        ▼
final checksum regeneration (generate_release_checksums.mjs, already implemented,
        re-run against the NOW-SIGNED bytes)
        │
        ▼
final publication bundle (generate_release_staging.mjs / buildFedosBetaPublicationBundleV1,
        already implemented, re-run against the new checksums)
```

**The critical correctness property this seam depends on** — proven with a real test in this Arc, not merely asserted — is that a signing step which mutates a file's bytes (as a real Authenticode signature embed always does) makes any checksum computed *before* that mutation instantly invalid, and the *existing*, unmodified `verifyFedosReleaseChecksums`/`verify_release_staging.mjs` machinery correctly rejects it as a `hash-mismatch` rather than silently accepting stale-but-plausible checksums. This was verified directly: a fixture installer file was checksummed, then its bytes were mutated to simulate an Authenticode signature block being embedded by a real `signtool sign` call, and `verifyFedosReleaseChecksums` correctly reported `hash-mismatch` against the pre-signing checksum while a checksum recomputed *after* the simulated mutation passed cleanly. No new verification engine was invented for this — the seam's safety comes entirely from reusing the existing, already-accepted hash-recompute-at-verify-time discipline.

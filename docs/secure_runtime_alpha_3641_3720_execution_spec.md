# Secure Runtime Alpha 3641–3720: Relay-Assisted Device Synchronization — Execution Spec

Architecture frozen. This Arc redesigns nothing: no change to the Device Registry, Registration Authority, Device Trust vocabulary, Device Sync Runtime, Sync Session/Package, Encrypted Device-to-Device Local Transfer (Alpha 3481–3560, commit `fcceca1`), the Sync Journal/Cursor/Allowlist, `FedosRelay`/`FedosConversationRelaySet`, or the existing proprietary private transport (`FedosPrivateTransport`) — all unmodified. ## Phase B — Route Decision

Compared:
- **A. NIP-17 Gift Wrap** — REJECTED. Genuinely absent from this checkout's history (Phase A.5); acquiring it would mean merging an unmerged sibling branch, out of scope for this Arc.
- **B. The existing `FedosPrivateTransport` route, wholesale** — REJECTED as the reuse target. Its routing is hard-bound to Direct-mode Conversation membership; Device Sync pairs Devices, never Conversation participants. Redesigning that routing would violate "do not redesign accepted architecture."
- **C. A new, dedicated proprietary Device Sync route, built from the ALREADY-REAL primitives** — ADOPTED. Reuses `FedosRelay`/`FedosConversationRelaySet` (Phase A.1–2, unmodified), `FedosNostrSigningAuthority.signEvent()` kind 1 (Phase A.3, unmodified), and the SAME "kind:1 + marker tag + base64 opaque content" wire idiom `FedosPrivateTransport`'s own event file already established — applied under a NEW, distinct marker tag (`["fedos-device-sync","1"]`) so it can never collide with that route's own traffic, a public Board post, or a NIP-17 Gift Wrap.
- **D. A generic, unstructured Relay event** — REJECTED. No versioning, no safety guarantee.

**Frozen route version**: `FEDOS_DEVICE_RELAY_SYNC_ROUTE_VERSION = 1` (`fedos_device_relay_sync_wire_payload.ts`). No silent fallback to any other route exists anywhere in this Arc — every construction/parse function is hard-wired to exactly this one version. **This Arc does NOT claim NIP-17 compliance of any kind** — the wire construction here follows no NIP-17 normative specification; it is this codebase's own proprietary convention, honestly labeled as such throughout.

## Phase C — Wire Payload V1

`FedosDeviceRelaySyncWirePayloadV1` (`fedos_device_relay_sync_wire_payload.ts`) — 12 fields: `schemaVersion`, `routeVersion`, `transferSessionId`, `sourceDeviceId`, `targetDeviceId`, `accountAuthority`, `accountPublicIdentifier`, `packageContentHash`, `encryptedPackageBase64`, `createdAt`, `expiresAt`, `deliveryId`. No plaintext Sync record, no private key, no Master Seed, no Sender-Key secret — `encryptedPackageBase64` is the SAME bytes `serializeFedosDeviceTransferPackageToBytes()` (Alpha 3481–3560, unmodified) already produces; this file never decrypts or re-shapes them. `packageContentHash` duplicates the binding already inside the Transfer Package's own Manifest, at the OUTER layer, so an inbound handler can cheaply detect a substituted/tampered payload BEFORE ever base64-decoding or attempting to open the inner package.

Bound cryptographically through TWO layers: (1) the OUTER Nostr signature (`FedosNostrSigningAuthority.signEvent()`, kind 1) covers the ENTIRE payload as JSON `content` — any tamper to any field invalidates it; (2) the INNER Transfer Package (Alpha 3481–3560, unmodified) already binds device/session/account facts via its own Manifest+Header+content-hash, established at Approval time through real mutual Schnorr authentication.

## Phase D — Outbound Coordinator

`FedosDeviceRelaySyncOutboundCoordinator.prepareAndPublish()` (`fedos_device_relay_sync_outbound_coordinator.ts`): (1) verify source Device live-trusted, (2) verify target Device live-trusted, (3) load the Transfer Session (must already be `"approved"` — the Invitation/Challenge/Proof/Approval handshake is `FedosDeviceTransferCoordinator`'s own, UNMODIFIED concern, completed before this file is ever called), (4) build the encrypted Sync Package — ONLY if no `FedosDeviceRelaySyncOutboxPersistence` record exists yet for this `transferSessionId` (proven by test: a second call never invokes `encryptionAuthority.build()` again; the cached, base64-serialized package is reused verbatim), (5) build the wire payload, (6) sign via `signEvent()` (kind 1), (7) publish to the configured Relay set via `FedosDeviceRelaySyncPublisher`, (8) record a per-Relay Observation fact per outcome, (9) return `{outcome, relayOutcomes}` as two SEPARATE fields — a Relay's own acceptance is never conflated with, or presented as, target Device import.

## Phase E — Inbound Handler

`FedosDeviceRelaySyncInboundHandler.handleIncomingEvent()` (`fedos_device_relay_sync_inbound_handler.ts`): (1) receive a candidate `FedosEventDescriptor`, (2) validate route/event shape, (3) dedup by the outer Relay event id (Phase F, layer 1), (4) verify the OUTER Nostr signature — reusing the EXISTING, unmodified `NobleSignatureVerifier` (real BIP-340 Schnorr, the SAME verifier `verifyFedosDeviceBindingAccountAuthorization()` already reuses) — a tampered event (any field, including the routing facts trusted next) fails closed here, BEFORE any of its claims are acted on, (5) verify the intended recipient Device/account, (6) dedup by `transferSessionId`+`packageContentHash` (Phase F, layer 2), (7) re-check LIVE Device Registry trust for BOTH source and target (revoked fails closed), (8) verify the outer content-hash binding BEFORE ever attempting decrypt, (9) open the encrypted Sync Package through the EXISTING, UNMODIFIED `FedosDeviceTransferCoordinator.verifyTransferPackage()` — no new decryption logic, no new tamper/expiry/replay check beyond what that Coordinator already proves, (10) on success, durably record the import fact, (11) produce one explicit, honest outcome. Never imports merely because the outer event was well-formed, relay-accepted, or even validly signed — every check above is independent and must all pass.

**Scope boundary, stated honestly**: this Arc assumes the Transfer Session's own handshake (Invitation → Challenge → Proof → Approval) has ALREADY completed through the existing, unmodified `FedosDeviceTransferCoordinator` — reaching `"approved"` — before this Arc's own new work begins. This Arc does not relay, redesign, or shortcut that handshake; its own new work begins at Package publish and ends at Package receive/decrypt/import, exactly the Target Flow named in this Arc's own instructions ("prepare encrypted transfer/session package" onward).

## Phase F — Deduplication

Durable, two-layer hierarchy over one record (`FedosDeviceRelaySyncInboundDedupPersistence`, in-memory + append-only NDJSON backends — never relies only on an in-memory set):
1. **`relayEventId`** (primary key, insert-only) — dedups the identical outer Nostr event arriving via multiple Relays (proven: "two Relays, duplicate inbound" imports exactly once).
2. **`transferSessionId`+`packageContentHash`** (secondary lookup) — dedups the SAME package republished under a DIFFERENT signed event (proven: cross-Relay dedup test, two distinct signatures, one import).

A third layer — Sync record identity — is inherited, unmodified, from `FedosDeviceTransferCoordinator.verifyTransferPackage()`'s own session-state-keyed duplicate/conflict detection, which runs AFTER this file's own two cheaper layers. Conflicting same-session/hash identity fails closed as `"conflict"` (durably failing the session), never silently accepted.

## Phase G — Retry

Retryable (this Arc's own `FedosDeviceRelaySyncPublisher`, per-Relay): timeout, transient publish failure — captured as a per-Relay `"failed"` outcome, `retryPolicy` left to the caller (this Arc records the fact; it does not itself loop retries — no unbounded retry of any kind exists in this Arc's own code). NOT retried, ever: a `"rejected"` per-Relay outcome (a real, explicit NIP-01 OK-false); and, at the Inbound layer, every hard denial (revoked Device, invalid signature, malformed route, tampered package, wrong recipient, expired transfer, disallowed Sync record) durably fails the session — never silently retried. Reuses the Observation vocabulary/pattern (Phase L) rather than a Board-specific Outbox type — this Arc's own `FedosDeviceRelaySyncOutboxPersistence` is a NEW, small, Device-Sync-scoped port, never `FedosBoardOutboxPersistence`/`FedosConversationTransportOutboxPersistence`.

## Phase H — Multi-Relay

`FedosDeviceRelaySyncPublisher` (`fedos_device_relay_sync_publisher.ts`) fans out to every configured Relay, in parallel, returning the FULL per-Relay outcome array (never aggregated into one value — Phase D/H's own explicit "record per-Relay outcome" requirement). One Relay's own timeout/rejection never corrupts another's result (proven by test: one accepts, one rejects, both outcomes present independently). `FEDOS_DEVICE_RELAY_SYNC_MAX_RELAYS = 16` — an explicit resource limit; constructing a Publisher over more Relays throws. No reputation/Sybil claim, no automatic Relay blocking, no hidden Relay discovery — every Relay in a set is explicitly, statically configured by the caller.

## Phase I — Device Revocation

If either Device becomes revoked: a NEW outbound transfer is denied (`"source-not-trusted"`/`"target-not-trusted"`, re-checked live at `prepareAndPublish()` time); an inbound, not-yet-imported package is denied (the SAME live re-check at `handleIncomingEvent()` time) — proven for revocation timing BEFORE publish, and AFTER publish but BEFORE import (both tested directly). Already-imported data is NOT remotely erased by this Arc — a Relay copy cannot be recalled (this Arc claims no deletion capability of any kind). The Transfer Session itself becomes terminal according to the EXISTING, unmodified Transfer rules (Alpha 3481–3560) — no re-trust of the same binding is possible (the Device Binding transition table has no outgoing edge from `"revoked"`).

## Phase J — Restart and Offline Delivery

Proven directly, using an in-process `FakeDeviceRelaySyncRelay` test fixture (`test/support/fake_device_relay_sync_relay.ts` — a REAL, functional `FedosRelay` implementation that actually stores published events and actually delivers OK-correlation/subscription messages, unlike `NullRelay`, which never invokes a registered listener at all): source publishes while the target has no active subscription at all; a LATER `subscribe()`+`onSubscriptionMessage()` call replays every already-stored, matching event (the exact "target offline then later receive" behavior); imports exactly once; source restart (a fresh `FedosDeviceRelaySyncOutboundCoordinator` over the same Outbox log) cannot duplicate a completed package (the underlying Transfer Session's own state machine forbids a second `buildTransferPackage()` call once `"package-sent"`); target restart (a fresh dedup persistence over the same NDJSON log) does not reapply an imported record; an expired package (received after its own `expiresAt`) is denied. **No real public Relay retention SLA is claimed anywhere** — every test uses the in-process fixture named above, never a real network Relay.

## Phase K — Sync Record Safety

Uses the EXISTING, unmodified `reviewFedosSyncRecordForJournal()`/`FEDOS_SYNC_ALLOWED_RECORD_TYPES` (`src/sync/fedos_sync_record_allowlist.ts`) directly — this Arc's own test file exercises it fresh against: an unknown record type, Master Seed, private key, Device private key, Sender-Key secret, bearer secret, passphrase, and raw plaintext metadata (all rejected via the existing sensitive-marker family or the closed-list check), plus an "executable/script payload" record type (rejected as unknown — no allowlisted type resembles it). The allowlist itself is NOT expanded — this Arc adds zero new record types. **Oversized payload**: a NEW, explicit resource limit this Arc DOES add — `FEDOS_DEVICE_RELAY_SYNC_MAX_CONTENT_BYTES = 256 KiB`, checked on the raw event `content` string BEFORE `JSON.parse()` is ever attempted (`fedos_device_relay_sync_event.ts`) — a genuine, narrow, reviewed addition this Arc's own instructions explicitly permit ("If a legitimate required record is missing, document and add only the narrow record type").

## Phase L — Observation and Status

`FedosDeviceRelaySyncObservationRepository` (`fedos_device_relay_sync_observation.ts`) — a NEW, small, Device-Sync-scoped, protocol-neutral repository (mirrors the EXISTING `FedosDeliveryObservationRepository`'s own shape — `id`/`subjectId`/`state`/`observedAt`/`reason`, deterministic id, immutable fact — without editing that existing, closed-union type). Tracks exactly the 9 states this Arc's own instructions name: `queued`, `publishing`, `relay-accepted`, `relay-rejected`, `relay-failed`, `received`, `imported`, `denied`, `expired`. `relay-accepted` and `imported` are NEVER collapsed — proven by test: both facts are independently present for one session's own status query. `queryFedosDeviceRelaySyncStatusForSession()` exposes a read-only, chronological status query by `transferSessionId`, across both local and every configured Relay's own branded subject id. No universal Relay reputation score of any kind exists anywhere in this file.

## Threat Model / Security Statement

**What this Arc's Relay-assisted transfer proves:**
- The Relay only ever holds: a `deviceId` pair (opaque, application-local strings), a public account identity, a package content hash, and one opaque base64 blob it cannot decrypt (the Transfer Package, itself sealed under the SAME self-ECDH-to-account-key construction Alpha 3321–3400 already established — unmodified, unchanged by this Arc).
- Any tamper to the outer Nostr event (any field, including the routing facts this file trusts) is caught by real BIP-340 Schnorr signature re-verification before any of its claims are acted on.
- Any tamper to, or substitution of, the Transfer Package itself (post-signing, in transit, or via a malicious Relay) is caught by the outer content-hash gate before any decrypt is attempted, or by the inner Coordinator's own Manifest/content-hash checks on a fresh decrypt.
- Both participating Devices' trust state is re-checked against the LIVE Registry at publish time and at import time — never cached, never trusted from an earlier snapshot or from the Relay's own claims.
- Duplicate delivery (same event via multiple Relays, or the same package via differently-signed republishes) imports exactly once, durably, across a simulated process restart.

**What this Arc's Relay-assisted transfer does NOT prove:**
- That the Relay actually stores or forwards anything, or for how long — no real public Relay retention SLA is claimed; every test uses an in-process fixture.
- That the Relay cannot be compelled to delete, or has actually deleted, anything — this Arc claims no Relay-deletion capability of any kind.
- That Relay-reported timestamps are canonical ordering of anything — this Arc's own dedup/expiry logic never trusts a Relay-supplied timestamp as authoritative; `createdAt`/`expiresAt` are the SENDER's own signed claims, checked against the RECEIVER's own local clock.
- Any distributed exactly-once guarantee beyond this Arc's own single-writer, in-process dedup persistence.
- Any Sender-Key secret synchronization of any kind — this Arc's own checkout contains no Sender-Key secret persistence code at all (confirmed absent from this checkout's history), and this Arc adds none.

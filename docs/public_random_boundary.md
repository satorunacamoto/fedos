# FedOS Core — Public Random / Nonce Boundary Design (Stage 103)

This document fixes the DESIGN of the future public `randomBytes` API and
its nonce-generation counterpart — extending
`docs/fedos_core_public_api_design.md` section 7 ("Nonce / random
generation is a separate boundary") into its own dedicated record, per
that section's own note that a future stage would fix this boundary
before any public `encrypt`/`decrypt` skeleton needs to consume its
output. As of Stage 103, `packages/fedos-core-rust/src/lib.rs` gains two
small, PUBLIC, label-only placeholder types —
`FedosRandomBoundary`/`fedos_random_boundary_status()` and
`FedosNonceBoundary`/`fedos_nonce_boundary_status()` — that mirror the
shape described below. Neither generates a byte.

## 1. Why random and nonce are two boundaries, not one

A general-purpose `randomBytes` call and the nonce an AEAD operation
needs are easy to conflate — both are "some random-looking bytes" — but
they have different correctness requirements. A nonce for a given
AEAD key must never repeat; a general-purpose random byte has no such
uniqueness obligation. Folding them into a single boundary risks a
future implementation reusing one code path (and its failure modes) for
both, when a nonce failure (reuse) is a catastrophic key-compromise risk
and a general `randomBytes` failure is not. Keeping them as two
independent placeholder types now — `FedosRandomBoundary` and
`FedosNonceBoundary` — keeps that design question open and explicit for
the stage that implements either.

## 2. Future design of `randomBytes`

The future `randomBytes` function is expected to:

- accept a fixed, bounded size SELECTED BY LABEL (e.g. a small enum of
  supported output lengths), never an open-ended, caller-supplied byte
  count — this avoids both unbounded-allocation risk and the appearance
  of a general-purpose "give me N bytes" primitive with no accountability
  for what those bytes are used for;
- return a result descriptor carrying only a state label, never the
  generated bytes' `Vec<u8>`/typed-array by way of this design record
  (the actual byte transport mechanism across the WASM/FFI boundary is a
  separate, later engineering decision, out of scope here);
- draw from a CSPRNG source whose adoption is reviewed as its own,
  dedicated future stage (see `docs/fedos_core_rust_safety.md` section 7
  and `docs/rust_dependency_adoption.md` section 6) — no such dependency
  exists in this crate today.

## 3. Future design of nonce generation

The future nonce-generation path is expected to:

- be consumed ONLY internally by a future `encrypt` implementation, never
  exposed as its own standalone public function a caller could invoke
  directly and reuse a value from — a nonce's uniqueness guarantee is the
  encrypt path's responsibility, not the caller's;
- be sized and structured per the AEAD algorithm selected (see
  `docs/fedos_core_public_api_design.md` section 5) — ChaCha20-Poly1305
  and AES-256-GCM both use a 96-bit nonce, but this document does not fix
  that as a permanent constraint, since a future AEAD candidate could
  differ;
- draw from the SAME CSPRNG source `randomBytes` eventually uses, once
  that source is adopted and reviewed — no such dependency exists in this
  crate today, and no code anywhere in this crate generates a nonce.

## 4. What this stage implements

Nothing beyond two label-only placeholder types and two accessor
functions:

- **`FedosRandomBoundaryState`** (`Unavailable` / `Placeholder`) and
  **`FedosRandomBoundary`** (carries only the state), returned by
  **`fedos_random_boundary_status()`** — permanently `Unavailable`.
- **`FedosNonceBoundaryState`** (`Unavailable` / `Placeholder`) and
  **`FedosNonceBoundary`** (carries only the state), returned by
  **`fedos_nonce_boundary_status()`** — permanently `Unavailable`.

Neither type accepts a size, a byte count, or any parameter of any kind;
neither function reads, computes, or generates anything. No CSPRNG
dependency is adopted this stage. No connection exists between these two
types and any other type in this crate — including each other beyond
both existing on the same public boundary.

# Secure Runtime Alpha 3881–3940: Electron Dependency and Build Spike — Completion Declaration (PARTIAL)

**This is a PARTIAL outcome, not a full completion.** Dependency addition, development build, blank/static-page window launch, secure `BrowserWindow` configuration, and packaging are all proven, directly, with real evidence. Repository-wide `npm run typecheck` compatibility is NOT proven — it is a real, disclosed, unresolved blocker this Arc stops at exactly, per its own "if the dependency or packaging tool cannot be added safely, stop at that exact boundary and document it honestly" instruction. See the Phase A doc's own "Retrospective" section for the full account of what was tried and why each mitigation was rejected.

## What this Arc proves

- **Electron `43.1.1` and `electron-builder 26.15.3` install cleanly as devDependencies** in this exact repository, on this exact Windows/OneDrive/Japanese-path-affected machine, from the mandated short-path worktree (`C:\wt\electron-build-spike`) — `npm install` succeeded, 280 packages added on top of the existing 49, `package-lock.json` grew by 3,756 insertions / 215 deletions (a step-change, exactly as `04`'s own review predicted, confirmed rather than merely estimated).
- **A real, secure `BrowserWindow` launches and renders the correct local page** — proven THREE independent ways: (1) an automated process-smoke test (spawn, confirm alive, `SIGTERM`, confirm clean exit — 25/25 new tests passing, including two dedicated lifecycle tests); (2) a manual, session-recorded observation during this Arc's own development: `Get-Process | Select MainWindowTitle` showed a real window titled exactly `"FedOS Desktop Build Spike"` (the page's own `<title>`), for both the unpacked development build AND the packaged executable independently; (3) a real graceful-close proof: `CloseMainWindow()` (a genuine WM_CLOSE signal, not a force-kill) on the main window correctly triggered `window-all-closed` → `app.quit()`, and all 4 Electron OS processes (main/GPU/renderer/utility) exited to zero, confirmed via `Get-Process` before/after.
- **Every mandatory secure `BrowserWindow` setting is proven, structurally and empirically**: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` (no blocker needed — proven compatible by the real launches above), `webSecurity: true`, no `enableRemoteModule`, no `@electron/remote`, no `eval`/`new Function()`, only `loadFile()` (never `loadURL`, never any `http(s)://`/`localhost` reference), `will-navigate` unconditionally denied, every `setWindowOpenHandler` call denied, every permission request denied by default, no business IPC channel anywhere, and the preload exposes exactly one `contextBridge` key — an immutable, frozen, three-field build-metadata object, nothing else.
- **A real packaging spike succeeds**: `electron-builder`'s `"dir"` (unpacked, no installer, no code signing) target produced a working `dist-electron-spike-package/win-unpacked/` directory containing `FedOS Desktop Build Spike.exe`, which launches and shows the correct window title (independently confirmed, same method as above). Build+package time: ~17 seconds, end to end, from a clean start. Packaged size: 348 MB total — but this Arc's OWN bundled code (`resources/app.asar`) is 12 KB; the entire 348 MB is the unavoidable Electron/Chromium runtime, not this Arc's own code (proven directly, not asserted, by listing the asar's own contents: exactly 4 spike files + one package.json, and by comparing folder sizes).
- **A real, meaningful packaging bug was found, understood, and fixed during this Arc's own development, not hidden**: `electron-builder`, run against this repository's root directly (no separate app-staging copy), initially bundled the FULL, real `@noble/curves`/`@noble/hashes` source (including `.ts` files) into the packaged app, despite an `extraMetadata.dependencies: {}` override that was supposed to prevent it — fixed via explicit `files` exclusion patterns (`!node_modules/**/*`, `!src/**/*`, etc.), re-verified: the asar now contains exactly this Arc's own 4 compiled files plus one `package.json`, confirmed via direct archive listing.
- **A SECOND, more serious real bug was found and fixed**: `electron-builder`'s own `extraMetadata` handling, in this exact version/configuration, mutated the REAL, on-disk root `package.json` in place during packaging (stripping `scripts`/`devDependencies`, injecting a spike-only `main` field) and did NOT correctly revert it afterward — discovered directly, more than once, during this Arc's own development (each time, root `package.json` was restored by hand from the intended, git-diffable content). Fixed with a defensive wrapper script (`run_electron_builder_spike_package.mjs`) that snapshots `package.json` before invoking `electron-builder` and restores it byte-for-byte afterward, REGARDLESS of outcome — re-verified stable across multiple consecutive packaging runs.
- **A THIRD bug, in this Arc's own test code, was found and fixed**: the packaging test suite's own "no secrets in bundled files" check called `asar extract-file <archive> <name>` without realizing this command writes its output to the FLAT basename of `<name>` in the invocation's own working directory (no separate output-path argument, no stdout content) — run against the repo root, this SILENTLY OVERWROTE the real root `package.json` with the archived, `extraMetadata`-rewritten copy, since one bundled file is itself named `package.json`. Fixed by running every `extract-file` invocation with `cwd` pointed at a dedicated, disposable scratch directory, never the repo root — re-verified stable across repeated runs.
- **Development scripts are additive and isolated**: `build:electron-spike`, `start:electron-spike`, `package:electron-spike`, `test:electron-spike` are all NEW; `typecheck`, `test`, `build:runtime`, `start:runtime` are byte-for-byte unchanged (verified in the new test suite itself, test #21). `npm test`/`npm run test:electron-spike` never launch Electron implicitly — only this Arc's own dedicated test file does, and only via an explicit subprocess spawn it also cleans up (`afterEach`).
- **Existing Desktop Host/Shell/Presentation/Renderer regression is fully green**: 77/77 tests across `secure_runtime_alpha_2841_2920_desktop_application_shell.test.ts`, `..._3081_3160_content_accessor.test.ts`, `..._3241_3320_presentation_boundary.test.ts`, `..._3401_3480_renderer_boundary.test.ts`, `..._3561_3640_host_bridge.test.ts`, unmodified, unaffected — confirming test EXECUTION (as opposed to standalone typecheck) is not disturbed by this Arc's changes.

## The one real, unresolved blocker (why this is PARTIAL)

`npm run typecheck` (the unmodified root `tsconfig.json`, run via the unmodified `typecheck` script) is NOT clean after this Arc's changes. Two compounding, fully understood, honestly disclosed causes:

1. **Electron's own transitive `@types/node` dependency** (`electron`'s own `package.json` declares `"@types/node": "^24.9.0"` as a real dependency — unavoidable simply by adding Electron at all) causes TypeScript to resolve `node:*` import specifiers' own per-module declarations repository-wide, turning 390 pre-existing `// @ts-expect-error` suppression comments (across ~130 files, this repository's own long-established convention for `node:fs`/`node:child_process`/etc. imports, since `@types/node` has never been installed here before) into "Unused directive" errors. Confirmed, empirically, that NONE of `tsconfig.json`'s own `"types"` allowlist, `"typeRoots"`, `"paths"`, or `"moduleResolution"` settings prevent this.
2. **This Arc's own new files**, living under `src/desktop/electron_spike/` per this Arc's own Phase C instruction, are ALSO swept into the root tsconfig's own blanket `"include": ["src", ...]` — where they conflict with its `"verbatimModuleSyntax": true` setting (a `.cts` file's forced CommonJS syntax) and lack DOM lib (the renderer script's `window`/`document` references). 6 additional errors, specific to these new files, that this Arc's OWN dedicated `tsconfig.electron-spike.json` (under which these same files typecheck perfectly cleanly) does not have.

**Both are typecheck-ONLY.** `vitest` uses its own esbuild-based transpilation (types stripped, never fully checked), so `npm test` and every existing test suite continue to pass unaffected — confirmed directly (77/77 existing Desktop tests, 25/25 new spike tests).

**Mitigations tried and rejected, each for a concrete, observed reason** (full account in the Phase A doc's own retrospective):
- An `npm overrides` redirect to an empty stub package: REJECTED — crashed `npm install`'s own peer-dependency resolution.
- A `postinstall` cleanup script (drafted, tested, confirmed working): REJECTED by this environment's own permission classifier (a legitimate supply-chain-sensitive category — code that runs on every future `npm install`), and, when presented directly to the user as a genuine fork, **the user chose to stop here and treat this as the blocker** rather than approve it.
- Editing the shared root `tsconfig.json`: out of this Arc's own authorized scope (not on its own "files expected to change" list; architecture-frozen).
- Mass-editing ~130 unrelated files' own `@ts-expect-error` comments: clearly out of scope (`"never touch unrelated layers"`).

This blocker does not affect anything this Arc itself claims proven above — it affects only the STANDALONE `npm run typecheck` command's own output, going forward, until a future Arc (with explicit authorization to either add a postinstall hook or reconcile the root `tsconfig.json`) resolves it.

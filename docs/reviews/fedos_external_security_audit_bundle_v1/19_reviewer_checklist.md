# Reviewer Checklist

A single, actionable checklist for whoever actually conducts the
external audit. Complements — does not replace —
[`03_review_order.md`](03_review_order.md) (what order to read code in)
and [`06_disclosure_policy.md`](06_disclosure_policy.md) (how to report
what you find). This checklist is about **getting set up and knowing
what's still open**, so the auditor's own time goes toward new findings,
not toward re-discovering what this bundle already tracked.

## Before you start

- [ ] Confirm the exact commit you were handed matches
      [`09_commit_manifest.md`](09_commit_manifest.md) (`git rev-parse
      HEAD`) — if it differs, treat every hash/count in `08`-`18` as
      unverified for your commit until you re-run the checks yourself.
- [ ] Read [`00_audit_package.md`](00_audit_package.md) end to end —
      it is the entry point for a reason.
- [ ] Confirm your own toolchain matches or exceeds
      [`08_version_manifest.md`](08_version_manifest.md)'s recorded
      versions, especially `wasm-bindgen-cli` (must match the pinned
      crate version exactly, `0.2.126` at time of writing, or the WASM
      build can silently misbehave per `docs/runtime_wasm_bindgen_version_policy.md`).

## Reproduce the evidence yourself (do not trust this bundle's own numbers blindly)

- [ ] `npm run build:wasm && npm run build:wasm:manifest`, then
      `sha256sum packages/fedos-core-rust/pkg/fedos_core_rust_bg.wasm`
      — confirm it matches `10f7fdb2e1f2e656013f68f591e452e49cfdbcf9f5822906054b02619730ff6a`
      (385,565 bytes). This is the single most load-bearing
      reproducibility check in the whole bundle — see
      [`12_hashes.md`](12_hashes.md).
- [ ] `sha256sum packages/fedos-core-rust/Cargo.lock` (generated by the
      step above) — confirm it matches
      `6bbdadb710b65b517ceb8d671f2bdbf37283d7373a73d0ed8debc1d895368155`.
      A mismatch means the dependency graph has drifted since this
      bundle was written — treat every crypto-primitive-version claim in
      [`17_crypto_inventory.md`](17_crypto_inventory.md) as needing a
      fresh look if so.
- [ ] `cargo test --release --manifest-path packages/fedos-core-rust/Cargo.toml`
      — confirm 639+ passed, and that any failure is the already-known
      `cargo_toml_has_exactly_ten_production_dependencies_after_k256_adoption`
      count-drift test (harmless, disclosed), not a new failure.
- [ ] `npm run typecheck` (root + electron-spike) — **not run by this
      addendum**; confirm clean modulo the two long-documented baseline
      errors named in the original audit-prep package's §16.
- [ ] From a genuinely clean tree (commit everything first, or use a
      disposable clone), run the full release pipeline
      (`npm run release:beta --prefix packages/fedos-desktop-electron-spike`)
      and record fresh installer/ZIP hashes into your own copy of
      [`13_release_artifact_inventory.md`](13_release_artifact_inventory.md)
      — this addendum could not do this (dirty tree at time of writing).

## Not yet done — do these as part of the real engagement

- [ ] Run `cargo audit` against the reproduced `Cargo.lock` and `npm
      audit` against both `package-lock.json` files — **neither has ever
      been run against this codebase** ([`10_dependency_manifest.md`](10_dependency_manifest.md)).
- [ ] Generate a real, standard-format SBOM (CycloneDX/SPDX) with
      dedicated tooling and diff it against
      [`14_sbom.md`](14_sbom.md)'s manually-assembled equivalent.
- [ ] Independently confirm the 27-accessor `expose_bytes_for_internal_*`
      `SecretHandle` count (re-run the grep yourself — see
      [`17_crypto_inventory.md`](17_crypto_inventory.md)) and trace every
      JS/TS call site's own zeroization discipline — the single largest
      open cryptographic-hygiene question named across this entire
      bundle, repeated by at least three prior reviews without ever being
      closed.
- [ ] Determine whether the TypeScript-side `@noble/curves` Schnorr path
      (Signed Deletion Request signing) and the Rust/WASM `k256::schnorr`
      path are ever asked to verify each other's signatures, and whether
      the TS-side path has its own KAT-vector-style test coverage
      equivalent to the WASM side's — a genuinely new question this
      addendum surfaced, not previously scoped by any prior review
      ([`17_crypto_inventory.md`](17_crypto_inventory.md)).
- [ ] Confirm whether `aes-gcm` (present, KAT-tested, but not confirmed
      production-reachable) has any real call site or is genuinely dormant.
- [ ] Fresh-grep the entire renderer and main-process code for any
      outbound network call besides the Relay WebSocket transport, to
      independently confirm [`16_third_party_inventory.md`](16_third_party_inventory.md)'s
      "no telemetry/analytics/CDN" claim, which this addendum carried
      forward from prior review work rather than re-verifying itself.

## Business/human decisions this bundle cannot make for you

- [ ] Whether to add a `LICENSE` file / `package.json` `"license"` field,
      and which license — currently entirely unset
      ([`15_license_inventory.md`](15_license_inventory.md)).
- [ ] Whether to acquire and configure a real code-signing certificate —
      the readiness-assessment logic to consume one already exists and
      is tested; only the certificate itself and the decision to buy one
      are missing ([`13_release_artifact_inventory.md`](13_release_artifact_inventory.md)).
- [ ] Whether to fill `SECURITY.md`'s vulnerability-reporting contact
      placeholder before commissioning the real audit
      ([`06_disclosure_policy.md`](06_disclosure_policy.md), unchanged by
      this addendum).
- [ ] Whether to merge the two orphaned audit-prep review commits
      (`8e730f25`, `6873d24f`) into `master`, per
      [`00_audit_package.md`](00_audit_package.md)'s own top
      recommendation #1.

## Severity triage

Use [`06_disclosure_policy.md`](06_disclosure_policy.md)'s existing
severity rubric (carried unchanged from the original audit-prep
package). Before labeling anything "NEW", check it against
[`05_known_issues.md`](05_known_issues.md) and this addendum's own
[`18_evidence_cross_reference.md`](18_evidence_cross_reference.md) first
— a finding that restates something already disclosed here should be
labeled **CONFIRMED**, not **NEW**, per this repository's own
established convention (`8e730f25` §19).

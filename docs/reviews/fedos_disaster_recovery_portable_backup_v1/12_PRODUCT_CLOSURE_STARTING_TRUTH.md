## Recovery Bundle format

`fedos_recovery_bundle.ts`/`_container.ts`/`_data_part_codec.ts` — a versioned (`v: 1`)
container: `sealedMasterSeedEnvelope` (the Identity Part, the verbatim sealed-envelope JSON
string) + an optional encrypted Data Part (manifest + content-hash-verified entries).
`FEDOS_RECOVERY_BUNDLE_INCLUDED_LOGS` (21 entries) / `_EXCLUDED_LOGS` (19 entries, device-bound
or session-bound — Direct Ratchet session/sealed-secret/reset/import/remote-public-key logs,
Peer Device announcement identity, Device Registry, sync-journal/dedup logs — deliberately never
restored, on the assumption the target starts genuinely empty) live in
`fedos_recovery_bundle_profile_selection.ts`. `fedos_recovery_bundle_commerce_and_settings_selection.ts`
adds 10 Commerce entries + `app-settings`.

## Encryption authority

`fedos_recovery_bundle_encryption.ts`'s `FedosRecoveryBundleEncryptionAuthority` builds/restores
via AEAD sealed under the SAME `FedosMasterSeedAuthority` handle the rest of the app uses —
`build()`/`restoreIdentity()`/`restoreDataPart()`. As of this HEAD, the production runtime
boundary for this path (`fedos_production_recovery_bundle_encryption_runtime_boundary.ts`) was
already fixed for the cross-WASM-instance opaque-handle defect in the immediately-preceding arc
— CLOSED for Recovery Bundle encryption specifically at this starting point.

## Restore Coordinator

`fedos_recovery_bundle_import_coordinator.ts` — `inspectFedosRecoveryBundle()` (pure plan, no
passphrase needed) + `restoreFedosRecoveryBundle()` (the real restore). Fails closed at every
stage; the Identity Part write (sealed Master Seed to disk) is the one stage with a real side
effect before Data Part validation completes. `target-not-fresh` at this starting point checked
ONLY `existsSync(request.targetPaths.sealedMasterSeedFile)` — narrower than the full set of
durable profile leaves (this is the exact root cause Phase A/Agent D's audit targets, closed by
Track 3).

## Electron IPC surface

`fedos_electron_beta_main.cts`: `fedos-profile:recovery-inspect` / `recovery-restore` /
`recovery-export` (`handleRecoveryRestore()` at the time of reading additionally gated on
`detectProfileState().presence !== "absent"` — the same narrow freshness definition, an
independent instance of the same root cause). `recovery-export` returns `bundleBase64` only —
no dedicated save-to-file channel exists yet (flagged for Track 1).

## Profile selection / fresh-device semantics

`fedos_profile_initialization_coordinator.ts`'s `detectProfileState()` is the ONE freshness-
detection method in the codebase, but at this starting point it inspects only
`profilePersistence` (`profile.json`) and `sealedSeedPersistence` (`master-seed.sealed.json`) —
never any of the other ~33 durable leaves `planFedosLocalProfilePaths()` names. This is the
starting condition Track 3 closes.

## Device-trust exclusion / re-establishment, Direct Ratchet re-establishment

By design, Device Registry and Direct Ratchet session/sealed-secret state are in the EXCLUDED
list above — a restored profile never resurrects the old device's trust state or an old Ratchet
session; a fresh device identity is always minted (`freshLocalDeviceId`, generated by the IPC
handler, never read from the bundle) and Ratchet sessions must be re-established peer-to-peer
after restore. This is honest-by-construction in the format itself, not something Track 3 needs
to add — Track 3's own scope is the SEPARATE identity-boundary gap (old identity's own data
surviving a Start-Over/restore-target reset), not Ratchet non-portability.

## Third-relaunch persistence proof / cross-WASM-instance fix history

The immediately-preceding arc's own real spawned-Electron-process IPC acceptance test
(`fedos_disaster_recovery_portable_backup_ipc_acceptance.test.ts`) and a real vertical-slice
test (`fedos_disaster_recovery_portable_backup_fresh_machine_restore_real_vertical_slice.test.ts`,
4/4 passing) already prove export → restore → restart(→unlock) for the DEV Electron binary. The
cross-WASM-instance opaque-handle bug (constructing a fresh WASM module per call, causing a
handle-mismatch that fails closed silently) was found and fixed twice before this arc began:
Conversation encryption (an earlier arc) and Recovery Bundle encryption (the immediately-
preceding arc). At this starting point it was NOT yet audited for Own-Device Sync — this is
exactly Phase A / Track 2's own scope.

## Existing tests / release pipeline state

Real, passing coverage existed for: bundle container/codec round-trips, profile-selection
inclusion/exclusion tables, export/import coordinators (dev-fake + real-crypto), the dev-binary

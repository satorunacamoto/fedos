## Requirement this places on the import coordinator (not yet written)

1. **Mint a fresh device identity on every restore** — never carry `profile.json.localDeviceId` or any device signing key forward from the bundle. Write a test asserting the restored profile's `localDeviceId` differs from the source's.
2. **Resolve the identity-transition residual question before shipping**: read `fedos_identity_transition_peer_runtime.ts`'s handling of an absent/stale local-decision record and confirm it cannot silently re-legitimize a peer identity the operator already superseded. If unsafe, the fix belongs in the peer runtime's own evaluation order, not in this arc's bundle format (do not patch around it here).
3. **The payload-retention staleness gap has no clean fix inside the bundle mechanism itself** (there is nothing newer to defer to on a fresh profile) — this is an **operator-facing disclosure requirement**, not a code fix: the restore UX (Agent D's flow) MUST show the bundle's export timestamp prominently before the operator commits, and the post-restore summary MUST state plainly that any deletions made *after* that export timestamp will not be reflected. This is the same honest-disclosure shape `docs/desktop_beta_user_guide_backup.md` already uses for cross-version restore risk — extend it, don't invent a new tone. Do **not** describe payload-retention/deletion state restored this way as "RECOVERED" in the final per-asset table — classify it **PARTIAL**, with the staleness caveat named explicitly, mirroring how `docs/desktop_beta_user_guide_archive_and_deletion.md` already handles the analogous Archive-restore case ("some previously-deleted content may come back... by design").
4. **Deletion-request lifecycle logs** (`deletion-request-state`, `-decision`, `-acknowledgement`, `-execution`, `-inbox-summary`, `-pending-review` — all six are included) are lower-severity than payload-retention (Agent C rates this P1, not P0: the underlying deletion effect is idempotent-by-`planId`, so restoring stale request bookkeeping does not on its own undo an already-applied deletion — but `deletionRequestStateLogFile` specifically is described by Agent C as a validated snapshot chain that **throws on out-of-order merge** rather than a safely-mergeable keyed event set. If the import coordinator ever needs to merge bundle data into anything other than a truly empty log (it shouldn't, per requirement in `01_recovery_bundle_format.md` — writes only to fresh, previously-nonexistent leaf files), this throw behavior is moot; if that assumption is ever relaxed, re-check this file specifically before doing so.

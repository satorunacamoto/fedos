# Direct Ratchet Cross-Account Identity-Space Mismatch — Competing Designs (Not a Decision)

**Status**: Bounded truthfulness audit, read-only design reconnaissance. Written against current HEAD of
`arc/fedos-installed-startup-root-cause`. **This document does not choose a design.** It reconstructs the
competing options the current code already implies, from source, so a future arc can make that decision with the
real trade-offs in front of it instead of rediscovering them.

**Non-goals**: no code in `fedos_direct_ratchet_outbound_integration.ts` or
`fedos_direct_ratchet_inbound_integration.ts` was touched to produce this document, and none should be touched to
act on it without a real design decision first. This document does not re-litigate whether the mismatch is real —
that was already confirmed live (`packages/fedos-desktop-electron-spike/test/direct_ratchet_bidirectional_packaged_binary_real_electron.test.ts`,
scenario c, 4 independent real packaged-binary launches, Bob's side durably stuck at `"initialization-required"`).

---

## 0. The mismatch, precisely (recap with exact citations)

Two structurally unrelated string identity spaces both call themselves "this local device's identity," and Direct
Ratchet's wire protocol mixes them without translation:

| | Space A — Device Pairing / Ratchet's own `localDeviceRef` | Space B — Peer Device Discovery's own `deviceId` |
|---|---|---|
| Generated by | `FedosProfileInitializationCoordinator` at profile-**create** time, once, from a fresh `FedosDeviceSigningKeypair`: `` `device-${deviceKeypair.publicKeyHex.slice(0, 16)}` `` (`src/os/messenger/desktop/onboarding/fedos_profile_initialization_coordinator.ts:462-464`) | `readOrCreateFedosLocalPeerDeviceAnnouncementIdentity()`, an **independent** 32-hex-char CSPRNG value, own durable file (`src/os/messenger/conversations/peer_device/fedos_local_peer_device_announcement_identity.ts:39,101-107`; format frozen at `docs/reviews/fedos-peer-device-discovery-current/06_PROTOCOL_CONTRACT_FREEZE.md` §5) |
| Persisted where | `FedosLocalProfileDescriptorV1.localDeviceId` (profile descriptor) | its own standalone identity file, never the profile descriptor |
| Backing keypair | `FedosDeviceSigningKeypair` generated at profile-create time; **the private half is never durably stored** (confirmed: `01_CURRENT_DEVICE_AUTHORITY.md` §1.3 — "process-memory-only... no durable Device-private-key storage exists anywhere") | a **second, separately generated** `FedosDeviceSigningKeypair`; only `devicePublicKeyHex` is persisted (identity file above), the private half is generated fresh and discarded per identity-file-creation call |
| Registry role | the key `deviceRegistry.getBinding(localDeviceRef)` is called with for **this node's own** Device (`fedos_direct_ratchet_device_pair_resolver.ts:164`) | the key a **peer's** announced device is registered under, via `PersistedFedosDeviceTrustAuthority.registerDevice({deviceId, ...})` (`06_PROTOCOL_CONTRACT_FREEZE.md` §7 item 2) |
| Who supplies it as `remoteDeviceRef` for a cross-account send | — | the **only** value `acceptance-peer-device-announcement-list-observed` (i.e. real Peer Device Discovery) ever exposes for a genuine external peer |

`FedosDirectRatchetOutboundIntegration.establishSession()` builds the wire `session-init` payload's
`senderDeviceRef` from **Space A** (`this.#deps.localDeviceRef`,
`fedos_direct_ratchet_outbound_integration.ts:257`) while the caller supplies `recipientDeviceRef` from
**Space B** (the only space a genuine cross-account `remoteDeviceRef` can come from,
`fedos_direct_ratchet_outbound_integration.ts:259`). On the receiving side,
`FedosDirectRatchetInboundIntegration.#receiveSessionInit()` checks
`payload.recipientDeviceRef !== this.#deps.localDeviceRef` — i.e. a **Space B** value against a **Space A**
value (`fedos_direct_ratchet_inbound_integration.ts:277`) — which can only ever match by literal string
coincidence, never by design. The same file's `#receiveSessionInit()` continuation additionally calls
`deviceRegistry.getBinding(payload.senderDeviceRef)` (line 326) expecting a **Space A**-shaped value there too,
compounding the same mismatch on the sender-identity side.

**Why the Registry lookup itself doesn't already fail this obviously**: `deviceRegistry.getBinding()` is a single,
shared, string-keyed lookup with no space tag on the key — it will happily return a real, `"trusted"` binding for
*either* a Space A `localDeviceId` (written by Device Pairing) or a Space B `deviceId` (written by a Peer Device
Discovery announcement), because both writers share the exact same `FedosDeviceRegistryPersistence` instance
(`fedos_desktop_runtime.ts`: `deviceRegistryPersistence!` passed into both `conversationDirectRatchetDeps` and
`conversationPeerDeviceAnnouncementDeps`). This is *why* `06_PROTOCOL_CONTRACT_FREEZE.md` §7 item 4 could
correctly assert "confirmed no cryptographic incompatibility" for `resolveFedosDirectRatchetDevicePair()` — that
function only ever calls `getBinding()`, which is genuinely space-agnostic. The mismatch lives one layer up, in
the **signable wire payload's own field semantics** (`senderDeviceRef`/`recipientDeviceRef` inside
`FedosDirectRatchetSessionInitPayloadV1`, `fedos_direct_ratchet_nip17_payload.ts:114-133`) and in **which space
each side's own `this.#deps.localDeviceRef` comparison implicitly assumes** — a layer §7 of the frozen contract
did not examine, because at the time it was written the question was "can the Registry hold both kinds of
binding" (yes), not "does the wire payload's own comparison logic agree on which space a value belongs to" (no).

## 1. Design option A — make Peer Device Discovery's `deviceId` canonical for Ratchet's own `senderDeviceRef`/`recipientDeviceRef`

**Shape**: Direct Ratchet stops using `config.localDeviceId` (Space A) as its own `localDeviceRef` entirely, and
instead uses this node's own PDD-announced `deviceId` (Space B, from
`readOrCreateFedosLocalPeerDeviceAnnouncementIdentity()`) as `deps.localDeviceRef` everywhere Ratchet reads it
today: `FedosDirectRatchetOutboundIntegration`/`InboundIntegration` construction
(`fedos_conversation_runtime.ts:768`), session binding (`fedos_direct_ratchet_session_binding.ts:16,18`), session
id construction (`fedos_direct_ratchet_device_pair_resolver.ts:202-217`), and the Rust sealing-context binding
(`fedos_direct_ratchet_session_binding.ts:24-28`, `local_device_ref`/`remote_device_ref` parameters to
`seal_direct_ratchet_secret`/`restore_direct_ratchet_secret`).

**Affected persistence formats**:
- `FedosDirectRatchetSessionRecordV1.binding.{localDeviceRef,remoteDeviceRef}` (`fedos_direct_ratchet_session_record.ts:24`)
  — no schema-shape change (still a plain string), but the *meaning*/*space* of every value written from this
  point forward changes. Any already-persisted session record (real ones only exist today from same-account/
  test-acceptance establishment — see §4 below) would carry a Space-A value that no longer matches this node's
  own `localDeviceRef` post-migration.
- `FedosSealedDirectRatchetSecretRecordV1` — sealed secrets are keyed/context-bound by
  `fedosDirectRatchetSealingDeviceContext(accountRef, deviceRef)` (`fedos_direct_ratchet_state_runtime.ts:370-371`,
  `:423-425`). A changed `localDeviceRef` value changes this context string, so **any already-sealed secret under
  the OLD `localDeviceRef` becomes unrecoverable** unless a one-time re-seal migration runs first (see §5).
- `FedosLocalProfileDescriptorV1.localDeviceId` (Device Pairing's own field) is **unaffected** by this option —
  Device Pairing keeps its own Space A identity for same-account multi-device purposes; only *Ratchet's own*
  consumption of "which value is my local device" changes.

**Wire/signable-content schema impact**: **none structurally** — `FedosDirectRatchetSessionInitPayloadV1`'s
`senderDeviceRef`/`recipientDeviceRef` fields (`fedos_direct_ratchet_nip17_payload.ts:127,130`) are already bare
strings with no space marker; they would simply start carrying Space B values instead of Space A ones. The
**signable content** (`FedosDirectRatchetSessionResetSignableContent`,
`fedos_direct_ratchet_session_reset_authentication.ts`) is unchanged in shape. This is the option with the
smallest wire-schema footprint.

**Migration considerations for already-real Registry data**: Peer Device Discovery's own Registry writes (§7 of
the frozen contract) already use Space B `deviceId` as the binding key for **peer** devices — those are
unaffected. What changes is **this node's own local binding**: Device Pairing registers *this* node under a
Space A `localDeviceId` (`fedos_device_binding_registration_authority.ts`, §1.4/1.5 of `01_CURRENT_DEVICE_AUTHORITY.md`).
Under this option, Ratchet would need to resolve its *own* Device binding by Space B `deviceId` instead — but
today **nothing registers this node's own PDD identity into the local Device Registry as a binding at all**
(PDD's identity file, §above, only self-announces to peers; it never calls `registerDevice()` for itself). A local
self-binding under Space B would need to be created (a new, additive Registry write — `deviceTrustEnabled`'s
existing same-account pairing flow would remain fully untouched, per the hard constraint that identity semantics
elsewhere must not change).

**Security-UI implications**: `FedosConversationSecurityStateController#gatherFacts()` already sources the
"chosen device" for Axes 2/3 from `peerDeviceAnnouncementListObserved()` (Space B) —
`fedos_conversation_security_state_controller.ts:90-98`. Under this option, that choice becomes fully coherent
end-to-end (the axis's device selection and Ratchet's own internal device identity finally agree), which is a
**strict improvement** in the axis computation's own honesty, not a new risk.

**Invariants a future implementation MUST preserve**:
- The prior investigation's confirmed guarantee — a never-announced/never-trusted device is rejected closed by
  `establishDirectRatchetSession()` (scenario k, real packaged-binary proof) — must still hold under whichever
  space `remoteDeviceRef` is resolved from; the Registry's own revoked/trusted gate
  (`resolveFedosDirectRatchetDevicePair()`) must not be weakened to make the two spaces "just work."
- `PersistedFedosDeviceTrustAuthority`'s existing **"one account per device id"** conflict rule (§1.5 of
  `01_CURRENT_DEVICE_AUTHORITY.md`) must continue to apply to whichever space becomes canonical — a Space B
  `deviceId` must not be reusable across two different accounts either.
- Same-account Device Pairing's own dual-signature bar and `localDeviceId` semantics (Space A) must be left
  completely alone — this option only changes what *Ratchet* reads as "my device," never what Device Pairing
  itself writes or verifies.

## 2. Design option B — a translation/mapping layer between the two identity spaces

**Shape**: introduce a new, additive, local-only lookup — e.g. `FedosDeviceIdentitySpaceLinkPersistence` —
recording `(localDeviceId [Space A] ↔ peerDeviceAnnouncementDeviceId [Space B])` pairs for devices this node knows
are the *same physical device* (starting with **this node's own** device: link `config.localDeviceId` to this
node's own PDD `deviceId` at startup, since both already exist independently and are each durable). Ratchet's
outbound/inbound integrations keep reading `deps.localDeviceRef` in Space A exactly as today (zero change to
`fedos_direct_ratchet_outbound_integration.ts`/`inbound_integration.ts` internals), but a thin adapter — inserted
at the exact two call sites that construct/consume the wire `senderDeviceRef`/`recipientDeviceRef` fields —
translates Space A ↔ Space B at the wire boundary only.

**Affected persistence formats**:
- **New** persistence type (additive only): the link table above. No existing record type's schema changes.
- `FedosDirectRatchetSessionRecordV1.binding.{localDeviceRef,remoteDeviceRef}` — a design choice must be made
  (and documented, not left implicit) about which space session *bindings* persist in: keeping them in Space A
  (today's behavior, zero migration) with translation applied ONLY at the wire boundary is the smaller-blast-radius
  sub-choice; persisting the *translated* Space B value would reproduce Option A's own sealed-secret-context
  migration problem without Option A's wire-schema simplicity benefit.

**Wire/signable-content schema impact**: **none** — the wire payload keeps exactly the same field shapes; the
translation is invisible to the wire format itself, only to the local process constructing/consuming it. This
preserves the frozen `FedosDirectRatchetSessionInitPayloadV1`/`FedosDirectRatchetMessagePayloadV1` shapes
byte-for-byte, which is attractive if any already-deployed peer needs to interoperate during a rollout window.

**Migration considerations for already-real Registry data**: none required for *peer* data (PDD announcements
already write Space B `deviceId` bindings as today). This node's own link entry is created once, locally, at
first startup after the feature ships — no coordination with any peer required, and no existing Registry row needs
to change.

**Security-UI implications**: the Security State Controller would need to consult the SAME link table (or a
narrow accessor over it) to resolve "the device I selected via `peerDeviceAnnouncementListObserved()` (Space B) is
the SAME session `directRatchetStatus()` reports on (keyed in Space A)" — today those two facts are already read
from *different* namespaces implicitly assumed compatible (see `fedos_conversation_security_state_controller.ts:90-101`,
where `chosenDevice.deviceId` — Space B — is passed straight into `directRatchetStatus(conversationId,
chosenDevice.deviceId)`, which ultimately reaches `resolveFedosDirectRatchetDevicePair()`'s `remoteDeviceRef` —
correctly Space B for a *peer's* device, since peers are never in Space A from this node's perspective; this
specific call site is NOT part of the mismatch, only this node's OWN `localDeviceRef` is). This option adds one
more indirection the axis computation must be proven not to silently bypass.

**Invariants a future implementation MUST preserve**:
- The translation layer must be **read-only inference over already-verified facts**, never a NEW trust decision —
  it must not, by itself, let a link entry substitute for the Registry's own revoked/trusted checks.
- A link must never be inferred/guessed (e.g. "same account, therefore probably the same device") — only ever
  recorded for a device this node can already prove is itself (its own two durable identities) or, in a future
  multi-device-peer extension, a link a human/device explicitly attested. This is the most likely place for a new
  vulnerability class (a wrong link silently spoofing device identity across the boundary) if built without a
  real proof requirement for peer-side links — same caution as `06_PROTOCOL_CONTRACT_FREEZE.md` §7 item 3's own
  "do not silently overwrite a re-keying" rule.

## 3. Design option C — search for an existing canonical identity primitive already in the repo

The task requires searching before assuming none exists. One genuine candidate was found:

### `devicePublicKeyRef` / `devicePublicKeyHex` — the device's own Schnorr public key

Both subsystems already populate the **same-shaped** field on `FedosDeviceBindingV1`:
- Device Pairing: `devicePublicKeyRef = challenge.devicePublicKeyHex`
  (`fedos_device_binding_registration_authority.ts`, cited at `01_CURRENT_DEVICE_AUTHORITY.md` §1.5, line 85-87).
- Peer Device Discovery: `registerDevice({..., devicePublicKeyRef: devicePublicKeyHex, ...})`
  (`06_PROTOCOL_CONTRACT_FREEZE.md` §7 item 2).

Unlike `deviceId`/`localDeviceRef` (opaque protocol-specific labels, generated independently and differently by
each subsystem), a device's own Schnorr public key is the actual cryptographic identity underneath both — in
principle the one value that is *supposed* to mean the same thing regardless of which subsystem is talking about
it. This is a real, already-present, already-populated primitive, not a proposal.

**The caveat that keeps this from being a free win, verified directly**: today the two subsystems generate **two
independent keypairs** for what may be the same physical device/process — Device Pairing's own
`deviceKeypair = generateFedosDeviceSigningKeypair()` at profile-create time
(`fedos_profile_initialization_coordinator.ts:462`) and PDD's own separate
`generateFedosDeviceSigningKeypair()` call inside `readOrCreateFedosLocalPeerDeviceAnnouncementIdentity()`
(`fedos_local_peer_device_announcement_identity.ts:101`) — with **zero code path connecting them**. So even
`devicePublicKeyRef` is not *currently* the same value across both subsystems for one physical device; adopting
this option would additionally require unifying which keypair each subsystem's local identity is derived from
(e.g. PDD reusing Device Pairing's already-durable `localDeviceId`-linked public key instead of generating a
second one) — which is really Option A or Option B's own migration work, wearing a different name. Recorded here
because the task requires it to be found and named, not because it is a shortcut around A/B.

**Affected persistence formats / wire schema / migration**: identical concerns to whichever of A/B actually
carries this out, since adopting `devicePublicKeyRef` as canonical is a *sub-choice* of "what value populates
Space A and Space B so they agree," not a fourth independent mechanism.

**Invariant this option would uniquely need to protect**: a device's Schnorr **public** key is safe to treat as a
stable identity (it's already published in every signed statement), but nothing here should ever be read as
license to reconsider the private half's own storage discipline (§1.3 of `01_CURRENT_DEVICE_AUTHORITY.md` —
"no durable Device-private-key storage exists anywhere," a deliberate scope boundary of the arcs that built both
subsystems) — that is a materially larger, separate security decision than identity-space unification.

## 4. What is NOT an option, and why (things a naive read of the code might suggest)

- **"Just relax the receiver's comparison to accept either space"** — rejected in the prior investigation's own
  framing (`direct_ratchet_bidirectional_packaged_binary_real_electron.test.ts` header, lines 47-54): even patching
  the `recipientDeviceRef` check alone would still fail `deviceRegistry.getBinding(payload.senderDeviceRef)` on the
  *sender*-identity side for the same underlying reason. A partial patch would look like it worked in isolation
  while leaving the sender side silently broken — worse than the current honestly-`"initialization-required"`
  state, not better.
- **"Widen the wire payload to carry both space values"** — would touch the frozen, signed
  `FedosDirectRatchetSessionInitPayloadV1`/`FedosDirectRatchetSessionResetSignableContent` shape (an explicit hard
  constraint of this audit's own mandate: no widening a frozen signable-content schema without a real design
  decision), and does not by itself decide which value the *comparison* should trust — it would just relocate the
  same open question into "which of the two fields wins."

---

## 5. Cross-cutting migration note (applies to whichever option is eventually chosen)

There is currently **no real cross-account Ratchet session in production data to migrate** — the only sessions
that have ever reached `"active"` in any run of this codebase are (a) same-account Device Pairing scenarios (never
exercised the cross-account payload path at all) and (b) the unilateral, receiver-role-only side of a cross-account
attempt (e.g. Alice's own side in the real packaged-binary test — genuinely `"active"` locally, but never
successfully paired with a live reciprocal session on the peer's side, since that is exactly the blocker). This
means whichever option is chosen has a **currently-empty real migration surface** — a genuine advantage for
landing a fix now rather than later, before any real user's session data would need a live re-keying/re-sealing
migration path.

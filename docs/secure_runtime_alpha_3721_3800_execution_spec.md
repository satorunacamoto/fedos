# Secure Runtime Alpha 3721–3800: Background Device Sync Scheduling and Conflict Resolution — Execution Spec

Architecture frozen. This Arc redesigns nothing: no change to the Device Registry, Registration Authority, Device Trust vocabulary, Device Sync Runtime, Sync Session/Package, the Encrypted Device-to-Device Local Transfer protocol (Alpha 3481–3560), Relay-Assisted Device Synchronization (Alpha 3641–3720), or the Sync Journal/Cursor/Queue/Conflict-Vocabulary/Allowlist (Alpha 2421–2500) — all unmodified. It turns the existing manually-invoked Relay Device Sync flow into a controlled, restart-safe background scheduling boundary, and introduces explicit, deterministic conflict classification and operator-visible resolution planning. This Arc does not create distributed consensus and does not promise arbitrary multi-writer convergence.

Base revision: worktree `C:\wt\device-sync-scheduler`, branch `arc/device-sync-scheduler`, based on commit `1c9c306` (Secure Runtime Alpha 3641–3720, "Relay-Assisted Device Synchronization").

## Phase A — Transport/Flow Inventory (source-verified, before any production edit)

1. **`FedosConversationTransportScheduler`** (`src/conversation/transport/fedos_conversation_transport_scheduler.ts`, Alpha 1471–1540) is the established "Scheduler hardening pattern" this Arc mirrors: `start()` throws if already running; `stop()` clears the interval and sets running false (does NOT wait for an in-flight tick — this Arc's own Scheduler adds that); `tick()` is single-flight via a cached, `.finally()`-cleared, `.catch(() => undefined)`-protected in-flight `Promise`.
2. **`FedosSyncState`** (`src/sync/fedos_sync_state.ts`, Alpha 2421–2500) is entirely in-memory, with no durable persistence of its own beyond `captureRecoverySnapshot()`/`restoreDeviceFromRecoverySnapshot()` (caller-driven). It keeps its OWN internal Device Registry (`registerDevice()`/`listActiveDevices()`), separate from the account-level `FedosDeviceRegistryPersistence` trust/binding Registry — fan-out on `recordLocalChange()` only reaches devices registered there. `applyPendingChanges(deviceRef, at)` unconditionally advances that device's Cursor past EVERY pending entry, "so no single conflicted/duplicate/archived entry can block everything after it" — an accepted, unmodifiable design this Arc builds around, never redesigns.
3. **`FedosSyncApplyResult`** exposes only `{changeId, conversationId, outcome: "applied"|"duplicate"|"conflict"|"archived-skip", conflict?: FedosSyncConflictKind}` — no `originDeviceRef`/`sequence`. A caller cross-references `syncState.journalEntries()` by `changeId` to recover those fields (this Arc's own `FedosDeviceSyncImportCoordinator` does exactly this).
4. **`classifyFedosSyncConflict()`** (`src/sync/fedos_sync_conflict.ts`, Alpha 2421–2500) is a pure, 4-value (`"none"|"duplicate"|"tombstone-vs-upsert"|"concurrent-update"`) entry-vs-entry classifier with NO Registry reference and NO record-allowlist awareness — it cannot detect a since-revoked origin Device or a disallowed record type. `FedosSyncState` keeps its own per-device, per-conversation "last applied" state in a PRIVATE field with no public accessor; this Arc does not add one (would widen the frozen Sync Journal shape).
5. **`FedosDeviceRelaySyncOutboundCoordinator`/`FedosDeviceRelaySyncInboundHandler`** (`src/device/relay_sync/`, Alpha 3641–3720) already prove one manually-invoked Relay-assisted transfer end to end, including dedup, revocation checks, and tamper detection. This Arc's own Scheduler depends on a NEW, narrow `FedosDeviceSyncAttemptFn` boundary (`fedos_device_sync_attempt.ts`) rather than importing that Coordinator directly — satisfying "must not own Relay identity truth" and keeping the Scheduler reusable over any transport a future caller injects.
6. **`reviewFedosSyncRecordForJournal()`** (`src/sync/fedos_sync_record_allowlist.ts`, Alpha 2921–3000) — a closed 6-type allowlist plus a 12-marker sensitive-value rejection list, unmodified, reused directly by this Arc's own richer Conflict Vocabulary (Phase H) for record-type review.
7. **Device Registry trust checks**: `FedosDeviceRegistryPersistence.getBinding(deviceId)`/`listBindingsForAccount(authority, publicIdentifier)` (`src/device/persistence/`) — the same live, re-fetched-every-call pattern every prior Device arc already established, reused identically by this Arc's own Target Planning and Import Coordination.
8. **Files expected to change**: new directory `src/device/sync_scheduler/` only, plus this Arc's own docs/tests/README blurb. Nothing under `src/device/binding_challenge/`, `src/device/persistence/`, `src/device/runtime/`, `src/device/relay_sync/`, `src/device/transfer/`, `src/sync/`, `src/conversation/`, `src/desktop/`, `src/nostr/`, or `src/runtime/` is modified.

## Phase B — Scheduler Ownership Decision

`FedosDeviceSyncScheduler` (`fedos_device_sync_scheduler.ts`) MAY own: schedule state (via the injected `FedosDeviceSyncSchedulePersistence` port), the next eligible attempt time per Schedule, a single-flight in-flight guard, target-Device planning, retry decisions, and shutdown waiting. It MUST NOT own, and does not: Device trust truth (reads `FedosDeviceRegistryPersistence`, never mutates it), Sync Journal truth (reads `FedosSyncState`, never bypasses `applyPendingChanges()`), Relay identity truth (depends on the injected `FedosDeviceSyncAttemptFn`, never imports Relay Sync internals), crypto secrets (touches none), canonical Conversation state (touches none). Dependency injection throughout the constructor (`FedosDeviceSyncSchedulerDeps`) — no global singleton anywhere in this Arc.

## Phase C — Explicit Activation

Background sync is disabled by default: the constructor never starts a timer. Five narrow lifecycle operations: `startSync()` (throws if already running — repeated start explicitly rejected, mirroring `FedosConversationTransportScheduler.start()`), `stopSync()` (async, safe to call repeatedly, WAITS for any in-flight tick before resolving — a real addition beyond that established pattern), `syncStatus()` (always available regardless of running state — a read-only query, never gated), `tickSync()`/`triggerSyncNow()` (both denied — "operation after stop denied" — while not running). No hidden timer exists when disabled. No Desktop UI/Shell file is touched by this Arc.

## Phase D — Single-Flight

`tickSync()` and `triggerSyncNow()` share the IDENTICAL guard the interval timer's own tick uses: a second call while one tick is already in flight returns the SAME `Promise` (mirroring `FedosConversationTransportScheduler.tick()` exactly). `stopSync()` awaits that same in-flight `Promise` (via `.catch(() => undefined)`, so a rejected tick never produces an unhandled rejection or blocks shutdown). A throwing/rejecting `attemptFn` is caught inside `#attemptSchedule()` and converted to a `{outcome:"failed"}` result — it never propagates, and the single-flight guard is always released via `.finally()`. Independent `FedosDeviceSyncScheduler` instances (separate `schedulePersistence`) are fully isolated from each other.

## Phase E — Target Planning

`planFedosDeviceSyncTargets()` (`fedos_device_sync_target_planning.ts`), pure: (1) queries trusted Devices from the LIVE `FedosDeviceRegistryPersistence` for the configured account, (2) excludes the local source Device and any non-`"trusted"` (`"pending"`/`"revoked"`/`"unavailable"`) binding via the SAME filter, (3) reads each target's own Sync Cursor (`syncState.getCursor()`), (4) constructs the minimum eligible range (`cursor.sequence + 1` .. the lesser of the Journal's own latest sequence and the configured range cap), (5) enforces `maxTargetDevicesPerCycle`, (6) produces a deterministic plan (sorted by `targetDeviceId`). Never inspects record content — allowlist enforcement stays exactly where it already lives (origin-time `reviewFedosSyncRecordForJournal()`, import-time `fedos_device_sync_conflict.ts`). Never infers "online" status from anything but a real signal this file has no access to — an offline target with a non-empty pending range remains eligible, exactly as Alpha 3641–3720's own mailbox-style Relay delivery already proves is safe.

## Phase F — Durable Schedule State

`FedosDeviceSyncScheduleV1` (`fedos_device_sync_schedule.ts`) is a pure state machine (`"pending"→{"in-progress","operator-required"}`; `"in-progress"→{"pending","completed","failed","operator-required"}`; the rest terminal), mirroring the `fedos_device_transfer_session.ts` pattern. Persists ONLY non-secret facts: `scheduleId`, `sourceDeviceId`, `targetDeviceId`, `fromSequence`/`toSequence`, `transferSessionId`, `state`, `attemptCount`, `nextEligibleAt`, `lastCoarseOutcome`, `createdAt`/`updatedAt`, `schemaVersion`. Event-sourced (mirroring the established repo-wide pattern): a versioned event codec (`persistence/fedos_persisted_device_sync_schedule_event_v1.ts`, `fedos_device_sync_schedule_event_codec.ts`) plus `in_memory_fedos_device_sync_schedule_persistence.ts` (Map-backed) and `append_only_fedos_device_sync_schedule_persistence.ts` (NDJSON, replay-on-read, fails closed on a corrupt/conflicting line) backends, both implementing `FedosDeviceSyncSchedulePersistence`. `reconstructFedosDeviceSyncScheduleRecord()` replays events (sorting non-`"created"` events by `at` ascending) through the SAME pure transition functions the live tick path uses.

## Phase G — Retry Policy

Closed retry directive vocabulary (`fedos_device_sync_retry_policy.ts`): `"immediate"|"later"|"never"|"operator-required"` (`"immediate"` is reserved for future extensibility — `classifyFedosDeviceSyncRetryDirective()` never actually produces it today). A closed 13-value `FedosDeviceSyncAttemptOutcomeCode` classifies actual attempt outcomes: `"relay-timeout"`/`"relay-disconnected"`/`"target-unavailable"`/`"crypto-temporarily-unavailable"` → `"later"`; `"revoked-source"`/`"revoked-target"`/`"invalid-signature"`/`"tampered-package"`/`"expired-transfer"`/`"disallowed-record"`/`"route-rejected-permanent"` → `"never"`; `"identity-conflict"`/unrecognized → `"operator-required"`. No arbitrary universal retry count exists anywhere in this Arc: an explicit, injected `FedosDeviceSyncAbandonmentPolicy` (`{maxAttempts, laterDelaySeconds}`) is REQUIRED — the constructor throws on a missing or malformed one (Phase G.4's own test).

## Phase H — Conflict Vocabulary

`FedosDeviceSyncConflictKind` (`fedos_device_sync_conflict.ts`), a closed 11-value vocabulary distinguishing `"identical-duplicate"` from `"safe-concurrent-append"` from `"immutable-record-conflict"` from `"operator-decision-required"` — never calling every duplicate a conflict, never collapsing invalid data (`"unknown-record-type"`/`"revoked-device-contribution"`) with concurrent-but-valid data. ADDITIVE over `classifyFedosSyncConflict()` (Alpha 2421–2500, unmodified, unwidened): that function's own output is supplied by the caller as `baseConflictKind` (never recomputed here, since `FedosSyncState` keeps its "last applied" state private — see Phase A.4) and enriched with record-allowlist status, LIVE Device Registry trust of the originating Device, and sequence/cursor-divergence detection. Priority order: record-type review → origin-trust check → missing-dependency (sequence gap) → duplicate → cursor-divergence → tombstone-vs-upsert → concurrent-update (further split by record-type domain semantics, Phase I) → none.

## Phase I — Domain-Specific Resolution

Uses actual domain semantics, never one generic last-write-wins resolver: insert-once/immutable records (e.g. `"conversation-identity-metadata"`) — identical duplicate is an idempotent accept, same-identity/different-content is a conflict, NEVER an overwrite; append-only events (`"capability-public-event"`) — different Devices' own entries safely coexist; tombstone/revocation facts — a later terminal fact is respected, an upsert attempting to reverse it is rejected, never applied; projections (`"search-canonical-id"`) — a stale, locally-re-derivable projection is superseded by local refresh, never blindly applied over newer local state.

## Phase J — Conflict Authority

`planFedosDeviceSyncResolution()` (`fedos_device_sync_conflict_authority.ts`) is an ADDITIVE resolver/planner: a pure, deterministic `PLAN_TABLE` mapping every `FedosDeviceSyncConflictKind` to one of 7 closed decisions (`"apply"|"skip-identical"|"defer-missing-dependency"|"reject-invalid"|"record-conflict"|"require-operator"|"retry-after-refresh"`), each carrying a coarse `reason`. Returns PLANS, never a direct mutation of Sync Journal/Cursor/Pending-Change state. Detection (Phase H), planning (this phase), application (Phase K), and observation (Phase L) are kept in four separate files.

## Phase K — Import Coordination

`FedosDeviceSyncImportCoordinator.importPendingChanges()` (`fedos_device_sync_import_coordinator.ts`) is a POST-PROCESSING enrichment layer over `FedosSyncState.applyPendingChanges()` (called exactly once per import) — it adds NO new Journal apply logic of its own. Every result is reclassified through the richer vocabulary, UNCONDITIONALLY — not only the subset the base classifier already flagged, since that classifier has no Registry reference and no allowlist awareness and therefore cannot, on its own, catch a since-revoked origin Device or a disallowed record type contributed through an otherwise-clean `"applied"`/`"archived-skip"` base outcome. The local Cursor position used for gap/divergence detection is tracked PROGRESSIVELY across a multi-entry batch (mirroring `applyPendingChanges()`'s own per-entry Cursor advance) rather than reused from one stale batch-start snapshot, which would otherwise spuriously flag every entry after the first in a batch as `"missing-dependency"`.

**Honest, documented atomicity model**: `FedosSyncState.applyPendingChanges()` is unchanged — it still advances the Cursor past EVERY pending entry unconditionally, by its own Alpha 2421–2500 design. This Arc does not, and cannot without redesigning that accepted behavior, make the Cursor itself stop at a blocking record. "The unresolved blocking record remains visible" (this phase's own requirement) is instead satisfied by a SEPARATE Conflict persistence (Phase L): every entry the richer classifier does not mark `"apply"`/`"skip-identical"` is durably recorded as an unresolved Conflict, independent of where the Cursor physically sits.

## Phase L — Operator-Required Conflicts

`FedosDeviceSyncConflictRecordV1` (`persistence/fedos_device_sync_conflict_persistence.ts`, 15 fields) — a DELIBERATE, DOCUMENTED simplification relative to this Arc's own event-sourced Schedule persistence: a Conflict record has only three real transitions (observed → reobserved 0+ times → resolved), so this uses a "full snapshot per write, last-write-wins by `conflictId`" NDJSON style rather than a per-transition event type. `conflictId` is deterministic (`${targetDeviceId}:${changeId}`). `observe()` never clears an existing `resolved: true`. Read-only query (`fedos_device_sync_conflict_query.ts`): `listUnresolvedFedosDeviceSyncConflicts()`, `getFedosDeviceSyncConflictDetail()`. Resolution commands ONLY for the four objectively-safe actions this Arc's own instructions name — `"accept-identical"`, `"discard-invalid"`, `"refresh-missing-dependency"`, `"acknowledge"` — gated per-`conflictKind` by `SAME_ACTIONS_BY_KIND`; `resolveFedosDeviceSyncConflict()` REJECTS (`"unsafe-action"`) any action not on that Conflict's own safe list. There is no "force overwrite canonical state" command anywhere in this Arc.

## Phase M — Restart Recovery

Schedule: `#recoverInterruptedSchedules()` scans `listAllSchedules()` at the start of every tick; any Schedule still `"in-progress"` (crashed mid-attempt) is moved back to `"pending"` via a `"retry-later"` event (`coarseOutcome: "interrupted-recovered"`) — reusing the EXISTING `"in-progress"→"pending"` transition-table edge already needed for the ordinary retry-later case, never a new transition. Proven directly: a fresh `FedosDeviceSyncScheduler` instance over the SAME durable append-only log file recovers a Schedule left `"in-progress"` by a simulated crash (an un-awaited, never-settling `attemptFn`) and completes it on its next tick. Conflict: `AppendOnlyFedosDeviceSyncConflictPersistence` replay-on-construct proven directly — an unresolved Conflict recorded before a simulated restart is still present, with its `conflictKind` intact, after a fresh instance re-reads the same log.

## Phase N — Resource Limits

`FedosDeviceSyncResourceLimits` (`fedos_device_sync_resource_limits.ts`): `maxTargetDevicesPerCycle` (32), `maxJournalRecordsPerRange` (500), `maxConcurrentTransfersPerTick` (4) — all three ENFORCED directly by Target Planning/the Scheduler's own tick loop; `maxRelayCount` (16) — enforced at the injected `attemptFn`/Relay Sync Publisher layer (Alpha 3641–3720's own `FEDOS_DEVICE_RELAY_SYNC_MAX_RELAYS`, unmodified), restated here only for one-place visibility; `maxRetainedScheduleHistory`/`maxRetainedConflictHistory` (10,000 each) — DECLARED policy inputs, honestly documented as NOT YET enforced by any compaction/pruning code in this Arc (neither append-only backend ever deletes a record).

## What was built

**Phase B/C — `src/desktop/navigation/`** (new directory, six files):
- `fedos_desktop_conversation_navigation_state.ts` — closed state vocabulary (`empty`/`opening`/`open`/`open-failed`), four pure constructors, no implicit transitions.
- `fedos_desktop_conversation_navigation_history.ts` — pure, immutable back/forward stacks (browser-tab semantics: a new navigation, including "close," clears `forward`).
- `fedos_desktop_conversation_window_title.ts` — pure window-title derivation from navigation state + an already-loaded `FedosConversationDetailView` (Direct: other active participant's id; Group: active member count).
- `fedos_desktop_conversation_window_controller.ts` — one window's orchestration: open/switch/close/back/forward/restoreLastOpened/render. Owns its own `FedosDesktopConversationListViewModel`/`FedosDesktopConversationDetailViewModel` + matching Renderer-family instances over the Presentation Boundary's single shared `.shell` — the deliberate multi-window-safety resolution documented in Phase A.
- `append_only_fedos_desktop_navigation_persistence.ts` — Navigation state persistence, following this codebase's own established append-only-NDJSON pattern exactly (never a new persistence engine): pin/unpin/recent-touch/last-opened events, folded into a snapshot on replay.
- `fedos_desktop_conversation_window_registry.ts` — multi-window state model + window lifecycle (`createWindow`/`disposeWindow`/`getWindow`), conversation pin state, recent-conversation list, last-opened restoration — all backed by the persistence file above.

**Phase D — Renderer Integration**: the Window Controller's `render()` reuses `FedosDesktopConversationListRenderer`/`FedosDesktopConversationDetailRenderer` (Alpha 3401-3480) verbatim — zero duplicated projection logic; only additional INSTANCES of the same classes, one set per window.

**Phase E — Electron Integration** (`packages/fedos-desktop-electron-spike/src/fedos_electron_navigation_*`, five new files, additive sibling of the existing Alpha 3881-3940 build spike — that file is untouched): a real `ipcMain`/preload adapter wiring `Window -> Host (this file) -> Renderer (per-window render()) -> Navigation (Controller/Registry)`. Constructs exactly one `FedosDesktopConversationUiPresentationBoundary` directly (never `FedosDesktopHostBridge`, which is untouched and unused here — see that decision's own rationale in the main file's header) and exactly one `FedosDesktopConversationWindowRegistry` over it. Ten closed, validated IPC channels (`fedos-nav:*`). Same secure `BrowserWindow` baseline as the existing spike (contextIsolation/nodeIntegration/sandbox/webSecurity, navigation/permission/new-window denial) — restated, never loosened. Loads the compiled root application graph (`dist/desktop/navigation/…`, `dist/desktop/presentation/…`) via a documented `new Function`-based dynamic-import workaround (TypeScript otherwise downlevels `import()` to `require()` under this package's own CommonJS tsconfig, which cannot load a real ES module).

Build wiring: `tsconfig.runtime.json` gained two new entry points (`fedos_desktop_conversation_window_registry.ts`, `fedos_conversation_creator_identity_authority.ts`) so `npm run build:runtime` emits the navigation graph to `dist/`; `copy_static_assets.mjs` gained one line to also copy the new HTML page; the isolated package's own `package.json` gained one new script (`start:navigation`). All additive; nothing existing was renamed, removed, or reinterpreted.

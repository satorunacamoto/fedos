# Secure Runtime Alpha 4741-4820 — Production Master Seed Runtime Activation & Secure Unlock

This document covers Phases B-N: the production Desktop crypto activation
authority, host-containment claims, the pinned artifact manifest, the build
pipeline, the capability-limited facade, real profile creation/unlock, secret
lifetime, lock/teardown, Electron security, the failure matrix, the threat
model, development-vs-production truth, the baseline/final comparison, and the
honest packaged-acceptance stop. Phase A is in
`secure_runtime_alpha_4741_4820_phase_a_gate_and_artifact_inventory.md`.

## Phase B — Production Desktop Runtime Crypto Activation Authority

`src/desktop/production_activation/fedos_production_desktop_crypto_activation_authority.ts`
introduces the ONE explicit production activation authority. It answers with
a CLOSED vocabulary, never a boolean:

```
permitted | unsupported-host | artifact-missing | artifact-invalid
| artifact-version-mismatch | unapproved-build | capability-not-allowed
| initialization-failed
```

Sequence (`authorizeAndActivateFedosProductionDesktopMasterSeed`), fail-closed
at every step, never throwing:

1. **Approved host?** — the request's `attestation` must satisfy the
   unforgeable `isFedosProductionDesktopHostAttestation()` (Phase C); a
   caller-controlled string / plain object → `unsupported-host`.
2. **Artifact present?** — the three pinned files
   (`fedos_core_rust_bg.wasm`, `fedos_core_rust.js`,
   `fedos_wasm_artifact_manifest.v1.json`) must exist → else
   `artifact-missing`.
3. **Read + parse** the wasm bytes and the manifest (structural validation)
   → malformed manifest = `artifact-invalid`.
4. **Approved build?** — when the caller supplies an `expectedCrate`, the
   manifest crate name/version must match → else `unapproved-build`.
5. **Import the JS glue** (capability-contained inside this authority) and
   collect its module-level export names.
6. **Verify the pinned manifest** against the REAL bytes (hash recomputed,
   never trusted) + the observed exports → maps to
   `artifact-version-mismatch` / `capability-not-allowed` / `artifact-invalid`.
7. **Initialize** via `initSync({ module: wasmBytes })` → throw =
   `initialization-failed`.
8. **Permitted** — returns only the capability-limited facade (Phase F) + the
   attested `appId`.

It never reads `NODE_ENV`, never touches `fedos_wasm_loader.ts`'s dev gate,
never fetches remotely, and never silently downgrades — every non-permitted
answer is explicit and terminal.

## Phase C — Host Attestation Boundary (capability containment, NOT host authenticity)

`fedos_production_desktop_host_attestation.ts`. The narrowest LOCAL evidence
that a request originates from the accepted Electron main package:

- `createElectronMainHostAttestation({ appId, appVersion })` is the ONLY way
  to mint a token; it is intended to be called only inside the isolated
  Electron main package (explicit dependency injection unavailable to
  renderer code).
- The token carries a module-private `unique symbol` brand that is never
  exported and never crosses the `contextIsolation: true` /
  `nodeIntegration: false` / `sandbox: true` boundary — a renderer, Worker,
  or arbitrary browser context cannot forge it, and a JSON round-trip of a
  real token drops the brand (verified in the suite).
- It carries only build-embedded, non-secret facts (`appId`, `appVersion`).

**Explicitly NOT claimed:** resistance to local malware or a modified binary.
This is capability containment — a wrong context cannot reach the production
crypto — not a proof of host authenticity.

## Phase D — Pinned Artifact Manifest

`fedos_production_wasm_artifact_manifest.ts` + the generated
`pkg/fedos_wasm_artifact_manifest.v1.json`. Safe facts only: `schemaVersion`,
`crateName`/`crateVersion`, `wasmFilename`/`jsGlueFilename`, `wasmSha256Hex`,
`capabilityProfile` (`desktop-master-seed-v1`), `allowedExports`
(`["FedosMasterSeedAuthority", "initSync"]`), `compatibilityVersion`,
`generatedAt`. `verifyFedosProductionWasmArtifactManifest()` recomputes the
SHA-256 from the real bytes (filenames are never trusted alone), pins the
capability profile + allowed export set, and confirms every allowed export is
actually present on the glue. Generated by the build pipeline; NO secret; NO
remote fetch. It lives in the gitignored `pkg/` — regenerated per clean
build, never committed.

## Phase E — Build Pipeline

`scripts/build_production_wasm_artifact.mjs` (`npm run build:production-wasm`)
runs a deterministic SEQUENTIAL pipeline, never Cargo and npm concurrently:
`cargo test` (native) → `cargo build --target wasm32-unknown-unknown
--release` (with the required `RUSTFLAGS='--cfg
getrandom_backend="wasm_js"'`, set per-invocation, no committed
`.cargo/config.toml`) → `wasm-bindgen --target web` → manifest generation
(`scripts/generate_wasm_artifact_manifest.mjs`). Measured on this
environment: wasm32 release build ~34s; artifact size 263 292 bytes (260 KB);
JS glue 42 KB. Output lands only in gitignored `pkg/`/`target/`; no generated
binary or manifest is committed; the existing `build:wasm` script is
unchanged (additive scripts only).

## Phase F — Capability-Limited WASM Facade

`fedos_production_wasm_master_seed_facade.ts`. After activation, the
initialized glue module is captured in a closure and NEVER returned. The
facade exposes exactly one method, `constructMasterSeedAuthority()`, which
reads only the `FedosMasterSeedAuthority` constructor, validates the produced
value structurally (never `instanceof`), and returns an opaque handle. No
arbitrary module access; the raw namespace is never handed to application
code. `Object.keys(facade)` is exactly `["constructMasterSeedAuthority"]`
(asserted).

## Phase G — Real Profile Creation

`fedos_production_master_seed_authority.ts` implements the SAME
`FedosMasterSeedAuthority` interface the coordinator already consumes, backed
by the facade — so the coordinator is UNCHANGED (adapter, not replacement).
`fedos_production_profile_activation.ts` is the assembler: it runs activation
and, ONLY on `permitted`, returns a real production authority; on any other
decision it returns an explicit `blocked` result. **There is no fallback to
the development seed double or a fake authority.** The acceptance suite
proves: real seed generation, real Argon2id + ChaCha20-Poly1305 sealing, only
sealed material persisted (the on-disk file starts `{"v":1,"kdf":"argon2id"`
and contains no plaintext secret), account identity derived, local Device
registered through real BIP-340 pairing proofs, Runtime starts, ready — with
the dev double NOT used anywhere.

## Phase H — Real Profile Unlock

Proven end-to-end in the suite: create → ready → `lock()` → a FRESH
production authority + FRESH coordinator reads the sealed material → correct
secret restores/unseals through real WASM → account identity matches the
persisted descriptor → Runtime reaches ready → identity is stable across the
relaunch. A wrong secret fails closed (`unlock-failed`, no running Runtime);
corruption/missing sealed material fails closed (`corrupt`). The failure is a
single coarse outcome — it never reveals whether partial passphrase bytes
were correct (Rust's AEAD open never distinguishes wrong-key from tamper).

## Phase I — Secret Lifetime (honest)

The unlock secret enters only as a `FedosProfileUnlockSecret` (prior Arc,
reused): `consume(fn)` hands the live `Uint8Array` to the WASM `seal`/
`restore_sealed` call exactly once, then best-effort zeroes and invalidates
the buffer even on throw. The production authority never logs the passphrase
or the sealed envelope, never stores the secret on a field, and never places
it on a result/config. Byte-oriented input crosses the WASM boundary as
`Uint8Array`, never a `string`. **Stated plainly:** JavaScript strings cannot
be reliably zeroized; where a string ever backs the input, erasure is
best-effort only. No memory-erasure guarantee is overclaimed.

## Phase J — Lock and Teardown

`FedosProductionMasterSeedAuthority.clear()` zeroizes the WASM-held seed
(Rust `clear()`), sets an irreversible `#cleared` flag, AND drops this
adapter's reference to the handle — so a post-lock crypto command cannot
reach a live seed through this object (a later `seal()` fails closed;
verified). The coordinator's `lock()` stops the Runtime, clears in-memory
material, preserves sealed durable state, and is idempotent (prior Arc,
unchanged). Repeated lock/shutdown is safe; no orphan Runtime or live seed
handle survives.

## Phase K — Electron Security

Preserved, unchanged: `contextIsolation: true`, `nodeIntegration: false`,
`sandbox: true`, local content only, the frozen preload API, the closed IPC
vocabulary. This Arc touches NO `.cts` main/preload file. The host
attestation is the dedicated, closed capability boundary; the production
crypto module, WASM loader, filesystem, and process are never exposed to the
renderer. (A dedicated closed IPC unlock command shape and renderer-side
rate-limiting were NOT added — see the honest stop in Phase L: the reviewed
Electron GUI passphrase-input boundary remains a future step, per the Alpha
1267 scope limit the prior Arc also honored.)

## Phase L — Packaged Application Acceptance (honestly blocked by environment)

Full completion requires a real packaged/unpacked Electron process to create
and unlock a profile through real WASM. In THIS environment that cannot be
run honestly: it is headless (no display for Electron's GUI subsystem),
Electron is not installed in `packages/fedos-desktop-electron-spike/`
(`node_modules` absent), and electron-builder packaging plus GUI automation
are out of reach. Per the spec's explicit clause, this is declared a
**partial completion** rather than faked. What IS proven, at the source /
Node-runtime level, is the entire chain a packaged app would exercise: real
WASM build → host attestation → activation authority → manifest verification
→ capability-limited facade → production Master Seed generate/seal/restore →
sealed material on disk → identity consistency → Runtime start → unlock →
lock → relaunch → unlock, all through real WASM with no dev double. The
remaining gap is exclusively the packaging + GUI process boundary.

## Phase M — Failure Matrix (all fail closed, no downgrade)

Covered by the acceptance suite: invalid host attestation
(`unsupported-host`); artifact missing (`artifact-missing`); hash mismatch /
tampered bytes (`artifact-invalid`); malformed manifest (`artifact-invalid`);
manifest version mismatch (`artifact-version-mismatch`); foreign capability
profile (`capability-not-allowed`); unapproved build identity
(`unapproved-build`); `initSync` throwing on otherwise-valid input
(`initialization-failed`); wrong unlock secret (`unlock-failed`, no Runtime);
missing/corrupt sealed material (`corrupt`); blocked activation yields NO
authority (no fallback). Every branch is an explicit closed decision — no
automatic downgrade to a dev/fake authority anywhere.

## Phase N — Structural Guards

- The existing dev-only path stays dev-only (its `NODE_ENV` gate and the
  dynamic-loader/dev-approval files are byte-for-byte unchanged); Workers and
  arbitrary browsers stay closed.
- The production authority is reachable only via a valid Electron-main host
  attestation; a renderer cannot mint one (module-private brand).
- No arbitrary WASM import: the facade exposes one constructor only; the raw
  module namespace is never returned.
- The pinned manifest carries no secret-shaped field (asserted).
- No passphrase persistence, no secret logging, no secret-bearing result.
- No new crypto algorithm; no Conversation/Device/Archive/Search redesign; no
  Rust/`lib.rs` change; `p2p/` and `.tmp_gen/` untouched.
- No new runtime dependency (only `@noble/*`, already present; `node:*`
  built-ins). No exact-export/count guard was weakened — none needed changing
  (this Arc adds only new files + additive scripts).

## Threat model (honest)

Raises the bar from "real production Master Seed crypto is unreachable" to "a
host-attested, hash-pinned, capability-contained production activation path
that produces real sealed seeds and unlocks them through real WASM." It does
NOT add cloud/custodial recovery, OS-keychain storage, hardware-backed keys,
or forgotten-passphrase recovery; it does NOT resist local malware, a
modified binary, or memory scraping; and it does NOT prove a packaged GUI
process (Phase L). At-rest confidentiality now rests on the real Argon2id +
ChaCha20-Poly1305 sealing (exercised here), not on a dev double.

## Development vs production truth

- **Development path (existing):** `FedosWasmMasterSeedAuthority` through the
  `NODE_ENV`-gated dev loader — appropriate for dev, closed in production.
  Unchanged by this Arc.
- **Production path (new):** `FedosProductionMasterSeedAuthority` through the
  host-attested activation authority + verified manifest — no `NODE_ENV`
  dependency. Proven to run real seed generation/sealing/restoration and full
  profile create/unlock in Node against the real artifact.
- **Not yet proven:** the same flow inside a packaged Electron GUI process
  (Phase L, environment-blocked).

## Baseline vs final comparison

- Baseline (`bda2c1f`): no compiled `pkg/`; real Master Seed crypto
  unreachable; onboarding used a dev seed double; production unlock honestly
  blocked.
- Final: real `pkg/` builds here (34s, 260 KB); real WASM master-seed
  lifecycle proven in Node; a complete production activation boundary (B-G)
  exists; the unchanged coordinator reaches ready and unlock through real
  WASM (17/17 acceptance tests); the dev gate is untouched; the only
  remaining gap is the packaged Electron GUI process (Phase L).

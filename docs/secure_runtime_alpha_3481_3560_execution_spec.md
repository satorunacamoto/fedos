# Secure Runtime Alpha 3481–3560: Encrypted Device-to-Device Local Transfer — Execution Spec

Architecture frozen. This Arc redesigns nothing: no change to the Device Registry, the Registration Authority (`src/device/binding_challenge/`), Device Trust vocabulary (`src/device/fedos_device_binding.ts`), the Device Sync Runtime (`src/device/runtime/`), the Sync Session/Package types (`src/device/sync_session/`, `src/device/sync_package/`), `src/sync/`, Conversation Runtime, Archive, Search, or Sender-Key; no new Rust/WASM primitive; no new dependency. It completes local encrypted transfer between two already-registered, already-trusted Devices of the SAME account — still no cloud, no relay, no synchronization daemon.

Base revision: worktree `C:\wt\device-local-transfer`, branch `arc/device-local-transfer`, based on `master`-equivalent tip `205a425` (Secure Runtime Alpha 3321–3400, "Device Registration Runtime Activation and Local Device Sync Foundation").

## Phase A — Protocol design

Seven steps, one Coordinator, one durable Session record per transfer attempt:

1. **Transfer Invitation** — the initiator creates a `FedosDeviceTransferInvitationV1` naming itself and a responder Device, both already `"trusted"` for the SAME account (`FedosDeviceTransferCoordinator.createInvitation()`). This is the ONE step this Arc's own instructions leave the physical channel to (QR code, local file, local network discovery — all equally out of scope; "Still NO relay... Only local encrypted exchange").
2. **Transfer Challenge** — the responder, upon receiving the Invitation, mints a `FedosDeviceTransferChallengeV1` (`FedosDeviceTransferCoordinator.issueChallenge()`) — a fresh nonce the initiator must sign, embedding the initiator's OWN live-looked-up public key.
3. **Transfer Proof of Possession** (the initiator's half of mutual authentication) — the initiator signs the Challenge with its own `FedosDeviceSigningKeypair` (`createFedosDeviceTransferProof()`).
4. **Transfer Approval** (the responder's half) — the Coordinator independently re-verifies the Proof against the EXACT Challenge it issued (re-checked against the LIVE Registry), then the responder signs its own Approval statement over the same Challenge (`FedosDeviceTransferCoordinator.approveTransfer()`), proving IT is live too — the mutual-authentication property Device Binding (a one-directional account→device proof) does not itself need.
5. **Transfer Package** — the initiator builds a `FedosDeviceTransferPackageV1` (a thin `sessionId` binder around the EXISTING, unmodified `FedosDeviceSyncPackageV1`, Alpha 3321–3400) after the Coordinator re-verifies the Approval (`FedosDeviceTransferCoordinator.buildTransferPackage()`) — zero new encryption logic; the SAME, unmodified `FedosDeviceSyncPackageEncryptionAuthority` builds it.
6. **Transfer Verification** — the responder's own check of an incoming Package (`FedosDeviceTransferCoordinator.verifyTransferPackage()`): a content-hash gate catches ANY byte deviation from what was recorded at build time (`"conflict"`) BEFORE ever attempting decrypt — a stronger, cheaper first-line defense than relying on AEAD auth alone — then the SAME, unmodified Package Reader opens it.
7. **Transfer Completion** / **Transfer Abort** / **Transfer Failure** — `completeTransfer()` (terminal success), `abortTransfer()` (voluntary cancellation, any non-terminal state), and an automatic `"failed"` transition on every hard cryptographic denial this Coordinator discovers on its own (plus an explicit `failTransfer()` for a caller-observed failure this Coordinator has no way to detect itself).

## Phase B — Why NOT a fresh Account Authorization per transfer

Compared: **A.** re-run the full Alpha 3161–3240 Account Authorization (a fresh kind-1 Nostr signature) for every transfer — REJECTED. Both Devices already passed that boundary once, at registration; requiring it again for every LOCAL transfer between two already-vetted Devices adds Nostr-signing-authority dependency and latency this Arc's own "local, frequent, both devices already vetted" use case does not need, and the task's own Requirements section omits "Account Authorization" from the reuse list (unlike the prior two Arcs, which explicitly named it). **B.** Device-level challenge-response only, re-checking LIVE Registry trust state at EVERY step — ADOPTED. A Device must currently be `"trusted"` to participate in Invitation, Challenge, and Approval (re-checked, never cached, at each step) — this reuses the Registration Authority's own live-trust vocabulary exactly, without re-deriving a new authorization signature.

## Phase C — Transfer Session state machine

`src/device/transfer/fedos_device_transfer_session.ts` — closed transition table: `invited -> {challenged, aborted, failed}`, `challenged -> {approved, aborted, failed}`, `approved -> {package-sent, aborted, failed}`, `package-sent -> {verified, aborted, failed}`, `verified -> {completed, failed}`, `completed`/`aborted`/`failed` terminal. Pure, synchronous, side-effect-free — mirrors `fedos_device_binding.ts`'s own discipline exactly. The Challenge's own `nonce`/`issuedAt`/`expiresAt` are denormalized directly onto the session record (`challengeNonce`/`challengeIssuedAt`/`challengeExpiresAt`) by `challengeFedosDeviceTransferSession()` — this lets the Coordinator deterministically reconstruct the EXACT `FedosDeviceTransferChallengeV1` a session issued (combined with a fresh, live Registry key lookup) without a second persistence read.

## Phase D — Persistence

`src/device/transfer/persistence/` — a DELIBERATELY SEPARATE event-sourced port and file tree from the Device Registry, the Alpha 3161–3240 Challenge Replay persistence, and `src/sync/` (mirrors those Arcs' own "separate persistence port per concern" instruction exactly). One immutable event per `(sessionId, eventType)` — each of `"challenged"`/`"approved"`/`"package-sent"`/`"verified"` fires at most once per session, and exactly one of `"completed"`/`"aborted"`/`"failed"` (the three terminal states) ever fires. Reconstruction applies events in FIXED canonical lifecycle order (never the log's own physical append order) — deterministic regardless of any accidental interleaving, and an invalid/out-of-order transition is ignored rather than nulling out an already-valid session (mirrors `reconstructFedosDeviceBindingRecord`'s own "if (next !== null)" discipline). In-memory and append-only (NDJSON, insert-only, fail-closed on corruption) backends mirror the Device Registry's own two backends exactly.

## Phase E — Duplicate Package vs. Conflict

A `"package-sent"` event records a sha256 content-hash binding over the WHOLE `FedosDeviceTransferPackageV1` object. `verifyTransferPackage()` compares an incoming package's hash against that recorded value BEFORE ever calling the Package Reader: an identical hash for an ALREADY-`"verified"`/`"completed"` session is `"duplicate-package"` (idempotent — re-decrypts and returns the SAME recovered session, safe to repeat); a DIFFERENT hash against an already-progressed session is `"conflict"` (a substituted or in-transit-tampered package, refused and the session durably failed) — this is a cheaper, stronger first-line integrity check than relying on AEAD authentication alone, though the reused Package Reader's own tamper detection (`"manifest-mismatch"`, AEAD auth failure collapsed to `"failed"`) still runs, unmodified, on every FRESH (first-time) verification and was already exhaustively tested in Alpha 3321–3400's own suite (not duplicated here).

## Phase F — Security discipline: automatic failure

Every hard cryptographic denial this Coordinator discovers on its own — `"invalid-proof"`, `"wrong-device"`, `"replayed"`, `"expired"`, `"invalid-approval"`, `"conflict"`, a bubbled non-`"opened"` Package Reader outcome — durably transitions the session to `"failed"` (via a private `#denyAndFail()` helper, a no-op if already terminal). Usage/structural outcomes (`"not-found"`, `"wrong-state"`, `"already-*"`, `"duplicate-package"`) never do. One deliberate exception: a bubbled non-`"built"` `buildTransferPackage()` outcome (e.g. `"key-unavailable"`) does NOT fail the session — an environmental/transient condition (the Master Seed Authority temporarily unavailable) stays retryable, proven directly by test (retry with a working encryption authority succeeds from the SAME, unfailed `"approved"` state).

## Phase G — Tests

Two files, 26 tests total. Real signatures (`RealFedosNostrSigningAuthority` + real `FedosDeviceSigningKeypair` Schnorr, the same test-only real-crypto stand-ins Alpha 3161–3240 established), real Device Registry (`InMemoryFedosDeviceRegistryPersistence`/`AppendOnlyFedosDeviceRegistryPersistence`, unmodified), real AEAD wiring (`FedosWasmDeviceSyncPackageEncryptionAuthority`, unmodified, via the SAME real-in-memory-round-trip-fake-boundary technique Alpha 1541–1610/3321–3400 already established, since this checkout has no compiled WASM artifact). Covers, by the task's own matrix: tampering (Transfer Package content-hash conflict, caught before decrypt), replay (a Proof over a non-matching Challenge denied and the session failed), wrong device (a Proof naming a different device's key than the Challenge itself named, denied via the key-mismatch check that runs BEFORE signature verification), wrong account (a responder belonging to a different account refused at Invitation creation), interrupted transfer (abort mid-flow, and a subsequent resume attempt refused), restart recovery (two independent Coordinators over the same NDJSON log files recover an identical, RESUMABLE session — proven by continuing the SAME transfer to `"approved"` after the simulated restart), duplicate package (idempotent re-verification), and transfer cancellation (`abortTransfer()`, plus `already-terminal` on a second attempt).

## Security Statement

- No raw Device secret key, account secret key, or AEAD key byte is ever returned by any new file in this Arc.
- This Arc adds NO new signature-verification primitive: `verifyFedosDeviceSigningSignature()` (Alpha 3161–3240, unmodified) is reused verbatim for both the Proof and the Approval, under two distinct fixed preimage prefixes.
- This Arc adds NO new encryption: the Transfer Package's inner `syncPackage` is built and read by the EXISTING, unmodified `FedosWasmDeviceSyncPackageEncryptionAuthority` — the SAME self-ECDH-to-own-account-key construction and `"Conversation"` `AeadAadDomain` Alpha 3321–3400 already established, with no change of any kind.
- Every participating Device's trust state is re-checked against the LIVE Registry at Invitation, Challenge, and Approval time — never cached or trusted from an earlier snapshot.
- A single-writer, in-process replay guard (inherited discipline from Alpha 3161–3240) — no distributed exactly-once claim is made. Unlike that Arc's own global nonce-replay persistence, THIS Arc achieves replay-safety through each Transfer Session's own unique `sessionId` plus its own denormalized, one-shot Challenge fields — a documented, deliberate simplification justified by Transfer Sessions being inherently single-use/ephemeral pairings, never a shared, long-lived namespace the way Device Binding Challenges are.
- No network, relay, or synchronization daemon of any kind is implemented — every artifact in this Arc is LOCAL, in-process/on-disk data and pure verification logic.

## What this Arc explicitly does NOT claim

- No claim that the physical channel carrying an Invitation or Transfer Package between two Devices is itself secure or authenticated — this Arc proves the DATA's own authenticity/integrity/confidentiality, independent of whatever local channel (QR code, USB, local file, local network) a future integration chooses.
- No claim that a Device revoked mid-transfer is retroactively un-transferred — revocation (re-checked live at each step) prevents FUTURE progress; it does not erase an already-recorded event.
- No distributed exactly-once guarantee, no forward secrecy claim beyond what the reused Sync Package encryption already provides (none added, none removed).

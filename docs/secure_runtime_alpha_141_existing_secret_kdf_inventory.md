## 2. Inventory

### 2.1 Master Seed — does not exist

No "Master Seed" or mnemonic concept exists in `src/` or
`packages/fedos-core-rust/src/`. The only substantive content is
design prose in `docs/vault_crypto_identity.md` §2: "Master seed: a
single high-entropy seed (BIP39 mnemonic → seed) generated by a vetted
library, held only inside the future crypto core" — explicitly
"organizational sketch only — not implemented, no derivation code."
`src/identity/recovery_policy.ts` (Stage 130) explicitly forbids "NO
password, recovery phrase, mnemonic, seed, backup, export, import,
sync, or authentication field of any kind, anywhere in this file."

### 2.2 Root Key — a label, not a key type

`FedosAeadAadDomain::RootKey` (`packages/fedos-core-rust/src/lib.rs:5823`)
is a fixed AEAD associated-data domain-separation **label**, not a key
type. Separately, `HkdfDomain::RootKey` (`lib.rs:2500`) is one of five
fixed domain labels a derivation call can target (see 2.3) — also a
label, not a stored key. No `RootKey` struct or persisted root-key
material exists anywhere.

### 2.3 HKDF / SHA / KDF — REAL, IMPLEMENTED, Rust-only

- `packages/fedos-core-rust/src/lib.rs:2604`
  `kdf_core::derive_secret_handle_internal(&SecretHandle, HkdfDomain) -> SecretHandle`
  — real HKDF-SHA256 (RFC 5869) via the `hkdf`/`sha2` crates. Takes an
  input `SecretHandle` and a fixed `HkdfDomain`, returns an output
  `SecretHandle`.
- `HkdfDomain` (`lib.rs:2498-2510`) is a closed, five-variant enum:
  `RootKey`, `Identity`, `Storage`, `Conversation`, `TestOnly`. Each
  variant maps to its OWN fixed, compile-time `&'static [u8]` salt and
  info string (`lib.rs:2519-2538`), e.g.
  `HkdfDomain::RootKey => b"fedos-hkdf-salt-root-key-v1"` /
  `b"fedos-hkdf-info-root-key-v1"`. The doc comment at `lib.rs:2491-2496`
  states this exists precisely "so keys derived for different purposes
  from the SAME input `SecretHandle` never collide, per
  `docs/crypto_test_vectors.md` section 5's domain-separation rule."
  `docs/crypto_test_vectors.md` §5 independently confirms: "Domain
  separation is mandatory. Every derivation carries a distinct,
  documented `info`/context so keys for different purposes never
  collide."
- `packages/fedos-core-rust/src/crypto/hkdf_bridge.rs:52-88`
  `derive_message_key_from_conversation_key_internal` bridges
  `ConversationKey → MessageKey` via `derive_secret_handle_internal`
  under the fixed `HkdfDomain::Conversation`.
- `packages/fedos-core-rust/src/crypto/nip44_message_keys.rs:184-`
  — a NIP-44 message-key HKDF-expand path.
- No `pbkdf`/`argon2` implementation exists anywhere — `argon2` is
  named only as a future candidate crate in `docs/vault_crypto_identity.md:100`
  and `docs/crypto_test_vectors.md` §6.
- **Key structural fact for Alpha 142/143:** `derive_secret_handle_internal`
  is domain-AGNOSTIC and chain-COMPOSABLE — it accepts any `SecretHandle`
  as input (including one that is itself the OUTPUT of a prior call to
  the same function) and returns a new `SecretHandle`. Multi-level
  derivation (`derive(derive(seed, A), B)`) is therefore ALREADY
  possible with ZERO new Rust code — the only gap is that `HkdfDomain`
  currently has no Protocol Root variants (Nostr/Session/ATProto) and
  no Account/Device-index parameterization (its `salt()`/`info()` are
  fixed compile-time constants, not caller-parameterized).

### 2.4 `FedosAeadKeyHandle` — opaque, no raw-byte exposure

`packages/fedos-core-rust/src/lib.rs:5676-5695`:
```rust
pub struct FedosAeadKeyHandle { inner: secret_handle::SecretHandle }
```
Holds an opaque `SecretHandle`, not raw bytes directly. Its own methods
— `pub(crate) fn inner(&self)` (5684) and a `#[cfg(test)]`-only

`kind()` (a fixed label string), no raw-byte getter, no public
constructor — the only way to obtain one is
`generate_aead_key_handle()` (`lib.rs:6207`).

### 2.5 `SecretHandle` — exists, Rust-only, never crosses the WASM boundary

## 3. Answers to the five confirmation questions

1. **Can the existing KDF be reused?** Yes. `derive_secret_handle_internal`
   is domain-agnostic and chain-composable (2.3) — it can implement
   ANY of the Option A–E hierarchies in Alpha 142 with no change to
   the derivation primitive itself.
2. **Is new Rust implementation needed?** Yes, but narrowly:
   `HkdfDomain` needs new Protocol Root variants (Nostr/Session/ATProto/
   future) and a design for safely parameterizing Account/Device index
   into the derivation context (its `salt()`/`info()` are currently
   fixed compile-time constants — see 2.3's closing note). No change to
   the HKDF primitive, `SecretHandle`, or the zeroize/secrecy discipline
   is needed.
3. **Can this be implemented without ever exposing raw secret bytes to
   JS?** Yes — the existing `expose_bytes_for_internal_*` pattern
   (2.7) and the `AeadKeyHandle`-style opaque-wasm-wrapper pattern
   (2.4/2.8) are a direct, proven precedent for exposing a Root/Account
   Handle to Desktop without ever exposing bytes.
4. **Does this contradict the existing Secret Handle policy?** No —
   `docs/secret_lifecycle_implementation_plan.md` §8, "No raw secret is
   ever exposed through the public API," is already the operative
   policy and is fully compatible with a Root/Protocol hierarchy built
   from opaque handles.
5. **Does the current Public Crypto API have derived-key functionality
   today?** No (2.12) — this Arc's own eventual implementation (a
   future Stage, not this one) would be the first to add it.

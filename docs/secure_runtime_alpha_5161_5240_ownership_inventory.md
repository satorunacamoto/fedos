## Phase C/D/E — composition summary

See `src/desktop/beta/fedos_desktop_beta_application_assembly.ts`'s own header for the full design rationale. In one sentence per phase:

- **Phase C (Navigation):** `FedosDesktopConversationWindowRegistry` constructed once per Boundary generation, over the SAME `viewerParticipant`/`navigationLogPath` across restarts (durable pin/recent/last-opened state genuinely persists across a confirmed Runtime restart, even though the in-process window-controller Map itself is rebuilt).
- **Phase D (Notification/Tray/Badge/Background):** Notification Coordinator and Background Lifecycle are Electron-global (constructed once, never rebuilt — neither holds a Runtime reference); Tray/Badge Coordinators are Runtime-bound (rebuilt on restart, over the fresh Navigation Registry + Boundary). The real Electron-side adapters (`FedosElectronNotificationAdapter`/`FedosElectronTrayAdapter`/`FedosElectronBadgeAdapter`, all Alpha 4261-4340/4341-4420, UNMODIFIED) are reused verbatim from `fedos_electron_badge_main.cts`'s own proven pattern.
- **Phase E (Device Sync):** closed via ONE additive Coordinator dependency (`deviceSyncSchedulerEnabled`/`deviceSyncAbandonmentPolicy`/`deviceSyncAttemptFn`, mirroring `archiveEnabled`'s own established pattern byte-for-byte) plus a `FedosDeviceSyncEventBridge` constructed in the Electron main before unlock. Verified end to end: a real Scheduler is constructed, `backgroundSyncEnabled` genuinely starts/stops it through the Settings Application Coordinator, and `deviceSyncPresentationWiring.handleEvent()` genuinely routes into the real Notification/Badge coordinators. Honest, disclosed: no trusted target Device exists in any tested scenario, so every real trigger reports an honest empty tick — matching Phase E's own explicit "Scheduler remains valid but idle" requirement, never a fabricated target.

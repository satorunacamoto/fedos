# Secure Runtime Alpha 427 — Minimal Rust Signing Boundary Implementation

**Status: this Stage is REVIEW ONLY. Implementation was attempted and
STOPPED per this Stage's own binding instruction. NO Rust file, NO
`Cargo.toml`, and NO TypeScript file is modified.** Stage 1 of Phase B
(Alpha 427–430). **Conclusion: Phase B is BLOCKED at this Stage.**

## 1. What Phase A already settled (recap, not repeated here)

Alpha 423 adopted Option A (a narrow WASM export following the
`AeadKeyHandle`/`AeadCiphertextHandle` precedent). Alpha 424 fixed the
authority's scope (Option D, `kind = {1}`, deterministic
`accountIndex`-derived pubkey, no caller-supplied `pubkey`/`id`/`sig`).
Alpha 425/426 specified the input/output shapes. None of that is
undone here — it remains the correct design for whenever
implementation becomes possible.

## 2. Why implementation cannot proceed today

This Stage's own binding instruction is explicit:

> "If a master-seed import boundary is required, review it separately
> and keep it opaque... If no safe seed authority exists, stop and
> report rather than improvising one."

Alpha 422 §13 already established, by direct inspection, that **no
real Master Seed material exists anywhere reachable at runtime, in
Rust or TypeScript.** Building `FedosNostrSigningAuthority` (or any
function that could produce a real signature) requires SOME upstream
Nostr Root, which requires SOME upstream Master Seed. Exactly two
paths exist to obtain one, and both were evaluated and rejected:

### 2.1 Path A — the authority generates its own seed internally

Rust already has a proven, safe CSPRNG export (`random_bytes_32()`,
Alpha 422 §1) that could seed a fresh `FedosMasterSeedHandle` entirely
inside Rust, never touching TypeScript. This is technically the
SAFEST path from a "secret bytes never leave Rust" standpoint — but it
is not fit for purpose: a freshly-generated random identity, thrown
away and regenerated on every process restart (nothing in this
repository persists WASM module state across reloads), means the
"signing authority" would produce a DIFFERENT Nostr public key every
session. Outbound Board posts signed this way would not be
attributable to any stable, recognizable user identity — defeating the
Arc's own Objective ("Desktop-owned outbound Nostr event creation"
using THE user's own already-derived identity, not a disposable one).
This path produces a technically-working but practically-useless
authority, and is rejected on those grounds, not a safety concern.

### 2.2 Path B — TypeScript supplies real seed bytes across the WASM boundary

Would require a NEW `&[u8]` (or similar) WASM constructor accepting
seed bytes from TypeScript. Before that call can happen at all, those
32 bytes must already exist somewhere in JS-reachable memory —
generated by, imported into, or read from storage by, TypeScript code.
Alpha 422 §13 confirmed no such source exists:

- `src/vault/types.ts:11` — "NO key generation, NO key derivation, NO
  seed storage" (types-only placeholder, `InMemoryVaultBoundary`/`NoopVaultBoundary`
  track only a locked/unlocked label).
- `docs/secure_runtime_alpha_144_recovery_threat_model_decision.md:108`
  — Master Seed backup/storage is "explicitly deferred to a future
  Storage Review," a decision made and never since revisited.
- `FedosRuntimeIdentity` (Alpha 422 §7) holds no byte array of any
  kind.

Building the WASM constructor now would not, by itself, create a safe
source for those bytes — it would just move the unsolved problem
("where do real seed bytes safely originate and live before this
call") one step closer to the boundary, while additionally requiring
TypeScript/JS memory to hold raw Master Seed bytes at least transiently
with no existing protected-memory or zeroization discipline on that
side (JS has neither). That directly strains Permanent Security
Invariant 1 ("Secret bytes remain inside Rust Secure Runtime") at its
true origin, not merely at the WASM call site — the invariant is best
read as "secret bytes are never *reachable* outside Rust," and Path B
would make them briefly reachable in JS by construction, every single
time. This is exactly the "casual raw `Vec<u8>` seed constructor"
this Stage's own instruction prohibits building without a dedicated
review — and that dedicated review (a real Vault/Storage boundary
deciding HOW a Master Seed is generated, imported, protected in
memory, and persisted) does not exist yet, has never been attempted,
and is explicitly out of THIS Arc's own scope (no Vault/Storage work is
named anywhere in Alpha 422–430's Objective or Expected Production
Areas).

## 3. Decision

**No safe seed authority exists. Per this Stage's own instruction,
STOP AND REPORT rather than improvise either Path A (practically
useless) or Path B (strains the permanent secret-locality invariant
without a reviewed protected source).** No `FedosNostrSigningAuthority`
struct is added. No new `#[wasm_bindgen]` export is added. No
`Cargo.toml` change is made — none was needed for this decision either
way (Alpha 422 §5). No TypeScript adapter file is added (Alpha 428/429
are consequently not attempted — see the Alpha 430 completion doc).

## 4. What remains valid for a future Stage

Alpha 423's Option A decision, Alpha 424's scope decision, Alpha 425's
input model, and Alpha 426's output model are all seed-independent
design decisions — none of them assumed a particular seed source. Once
a future, dedicated Master Seed authority exists (see the Alpha 430
doc's recommended next Arc), THIS Stage's own §2 analysis identifies
exactly what that authority must provide: a way for
`FedosNostrSigningAuthority` to obtain a real `FedosProtocolRootHandle`
(Nostr Root) that is (a) NOT a fresh random value discarded every
session, and (b) NOT sourced from raw bytes sitting unprotected in JS
memory immediately before a WASM call.
